2.核心原因

该问题的本质是Selector 的 select 和 register 操作存在锁竞争，且 select 的阻塞特性会长期占用核心锁，导致 register 因无法获取锁而永久阻塞。

2.1 Selector 的三个 select 相关方法

当调用 select(long timeout) 时，入参timeout的取值有三种情况：

  1. timeout = 0：表示永久阻塞，直到满足「有就绪的 IO 事件」或「调用 selector.wakeup ()」或「线程被中断」这三个条件之一，才会返回；
  2. timeout > 0：表示超时阻塞，阻塞指定的毫秒数，超时后无论是否有就绪事件，都会自动唤醒并返回；
  3. timeout < 0：抛出 IllegalArgumentException 非法参数异常。

而无参的selector.select()方法，底层就是调用selector.select(0)。

2.2 SelectorImpl 锁机制

SelectorImpl为保证线程安全，在 select 和 register 操作中使用了同一组核心锁：

  • Selector实例锁：保护 Selector 整体状态
  • publicKeys锁：保护注册的 SelectionKey 集合（核心竞争点）
  • publicSelectedKeys锁：保护就绪的 SelectionKey 集合

2.3 WindowsSelectorImpl阻塞放大

Windows 平台下的WindowsSelectorImpl进一步放大了阻塞问题：

  1. doSelect方法中，subSelector.poll()最终调用 native 方法poll0，阻塞在操作系统层面（Windows 的WSAPoll），直到有 IO 事件 / 超时 / 被唤醒；
  2. 为处理大量 FD，WindowsSelectorImpl 还会创建辅助线程（SelectThread），但辅助线程的 poll 同样依赖锁机制，不会释放publicKeys；
  3. implRegister还额外依赖closeLock锁，进一步加固了阻塞。

2.4 时序导致的竞争

当执行顺序为select（阻塞）→ register时，锁竞争链如下：

线程 A（Worker，执行 select） 线程 B（Main，执行 register）
1. 获取 Selector 实例锁 -
2. 获取 publicKeys 锁 -
3. 获取 publicSelectedKeys 锁 -
4. 进入 doSelect，阻塞在 native poll0 -
5. 持续持有所有锁（直到 select 返回） 1. 尝试获取 publicKeys 锁
2. 发现锁被线程 A 持有，进入阻塞
3. register 无法继续执行
