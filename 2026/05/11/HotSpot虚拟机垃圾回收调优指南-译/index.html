1 垃圾收集调优简介

从桌面上的小型小程序到大型服务器上的网络服务，各种各样的应用都使用了 Java 平台标准版（Java SE）。为了支持这种多样化的部署方式，Java HotSpot 虚拟机提供了多种垃圾回收器，每种都旨在满足不同的需求。Java SE 根据应用程序运行的计算机类型选择最合适的垃圾回收器。然而，这种选择可能并不适用于每个应用程序。对于有严格性能目标或其他要求的用户、开发人员和管理员来说，他们可能需要明确选择垃圾回收器并调整某些参数以达到期望的性能水平。本文档提供了相关信息，以帮助完成这些任务。

首先，会以串行、stop-the-world式收集器为例，介绍垃圾收集器的一般特征以及基本的调优选项。然后，还会介绍其他收集器的具体特性，并说明在选择收集器时应考虑的因素。

什么是垃圾收集器？

垃圾回收器（GC）自动管理应用程序的动态内存分配请求。

垃圾回收器通过以下操作实现自动动态内存管理：

  • 向操作系统申请内存，并将内存归还给操作系统；
  • 按照应用程序的请求为其分配内存；
  • 判定内存中哪些区域仍被应用程序存活引用；
  • 回收未被使用的内存，以供应用程序重复利用。

Java HotSpot 虚拟机的各类垃圾回收器采用多种技术，提升上述内存管理操作的执行效率：

  • 采用分代回收结合对象年龄晋升机制，将回收工作重点集中在堆内存中可回收内存最多的区域；
  • 借助多线程实现回收操作并行执行，或将部分耗时较长的回收任务置于后台，与应用程序并发运行；
  • 通过存活对象压缩整理，规整内存布局，从而回收出更大的连续空闲内存。

为何垃圾回收器的选择至关重要？

垃圾回收器的作用是让应用开发人员无需进行手动动态内存管理。开发人员不必再手动匹配内存分配与内存释放操作，也无需精细管控已分配动态内存的生命周期。这彻底规避了部分内存管理类程序错误，代价是会产生一定额外运行时开销。Java HotSpot 虚拟机提供了多种垃圾回收算法可供选择。

何时需要重视垃圾回收器的选型？对部分应用而言，答案是无需选型。这类应用即便在垃圾回收产生停顿时，也能保持良好运行，且停顿频率适中、耗时较短。但对于一大类应用场景则不然，尤其是数 GB 级海量数据、多线程、高事务吞吐的应用。

阿姆达尔定律（特定问题的并行加速比受限于其串行执行部分）表明：绝大多数工作负载无法做到完全并行化，总有一部分逻辑只能串行执行，无法享受并行带来的性能增益。目前 Java 平台支持四种垃圾回收器，除串行 GC外，其余均通过将回收任务并行化来提升性能。尽可能压低垃圾回收的性能开销至关重要，可参考下述示例。

串行收集器通常足以适配绝大多数小型应用，尤其是在现代处理器上堆内存上限约 100MB 以内的应用。其他垃圾收集器会产生额外开销与复杂度，这是为换取专属回收特性所付出的代价。如果应用不需要其他收集器的定制化能力，直接使用串行收集器即可。

有一种场景不适合选用串行收集器：部署在大内存、双核及以上处理器服务器上的大型高多线程应用。应用运行在这类服务器级硬件环境时，虚拟机默认采用 G1（Garbage-First）收集器，具体可参阅 JVM 自适应Ergonomics机制。

2 自适应调度机制

JVM 自适应机制，是指 Java 虚拟机（JVM）结合垃圾回收启发式算法（如基于行为的启发式策略），提升应用程序性能的一套运行机制。

JVM 会依据运行平台，自适应默认选择垃圾回收器、堆内存大小以及即时编译器。这些默认选型能够适配不同类型应用的运行需求，同时大幅减少人工命令行参数调优工作。此外，基于行为的调优会动态调整堆内存各区域大小，使应用达到预设的运行表现。

本节将介绍上述默认选型规则与基于行为的自适应调优策略。建议优先使用默认配置，再酌情采用后续章节介绍的精细化参数配置。

垃圾回收器、堆内存及即时编译器默认选型

以下为垃圾回收器、堆内存大小、即时编译器的核心默认配置：

  1. 默认采用 G1（Garbage-First）垃圾收集器
  2. GC 最大线程数由堆内存大小和可用 CPU 资源共同限制
  3. 初始堆内存：物理内存的 1/64
  4. 最大堆内存：物理内存的 1/4
  5. 启用分层编译，同时使用 C1、C2 编译器

基于行为的调优

Java HotSpot 虚拟机的垃圾回收器可配置为优先满足两大目标之一：最大停顿时间、应用吞吐量。

当优先目标达成后，回收器会尽可能优化另一项目标。

当然，这两个目标并非总能如愿实现：应用需要最小堆内存以容纳全部存活数据，同时其他配置限制也可能导致无法达成部分乃至全部预期目标。

最大停顿时间目标

停顿时间，是指垃圾回收器暂停应用执行、回收闲置内存空间所消耗的时长。设置最大停顿时间目标，旨在限制垃圾回收产生的最长单次停顿耗时。

垃圾回收器会持续维护 GC 停顿的平均耗时及其方差。该平均值从程序运行伊始开始统计，并采用加权算法，使越近期的停顿时间权重越高。一旦停顿时间的平均值与方差之和超出最大停顿时间目标，垃圾回收器就判定该目标未达成。

可通过命令行参数 -XX:MaxGCPauseMillis=<nnn> 设定最大停顿时间目标。该参数作为指导性建议，告知垃圾回收器期望将停顿时间控制在 nnn 毫秒及以内。垃圾回收器会动态调整 Java 堆大小以及其他垃圾回收相关参数，力求把 GC 停顿控制在设定毫秒值之下。

不同垃圾回收器的默认最大停顿时间目标各不相同。这类自适应调整可能导致垃圾回收触发频次增加，从而降低应用整体吞吐量。但在部分场景下，系统仍无法达到预期的停顿时间目标。

吞吐量目标

吞吐量目标以垃圾回收耗时为衡量依据，程序运行中除去垃圾回收的其余时间，均视为应用业务运行时间。

可通过命令行参数 -XX:GCTimeRatio=nnn 设置吞吐量目标。垃圾回收耗时与应用运行耗时的比值为：$\boldsymbol{1/(1+nnn)}$。

例如：配置 -XX:GCTimeRatio=19，代表设定总运行时间的 1/20（即 5%）用于垃圾回收。

垃圾回收耗时是所有GC 停顿的累计总时长。若未达成吞吐量目标，垃圾回收器可采取的优化策略之一是扩大堆内存，以此延长两次垃圾回收间隔内的应用正常运行时间。

内存占用

当吞吐量目标和最大停顿时间目标均已满足时，垃圾回收器会主动收缩堆内存，直至其中某项目标（通常都是吞吐量目标）无法维持。

可以通过 -Xms=<nnn> 和 -Xmx=<mmm> 分别设置垃圾回收器可使用的最小堆大小与最大堆大小。

调优策略

堆内存会自动扩容或收缩，调整到刚好能满足选定吞吐量目标的大小。可学习堆调优相关策略，包括设置最大堆大小、配置最大停顿时间目标等。

除非明确业务所需堆内存大于默认最大堆，否则不建议手动指定最大堆容量。应根据应用实际负载，设置适配的吞吐量目标。

应用运行行为发生变化，会触发堆的扩容或收缩。例如：当应用对象分配速率升高时，堆会自动扩容，以维持原有吞吐量水平。

若堆已经扩容至设定上限，但仍无法达成吞吐量目标，说明当前最大堆设置偏小，不足以支撑吞吐量要求。可将最大堆大小调整至接近整机物理内存总量，但不能触发应用内存交换（Swap）。重新启动应用，若依旧无法达标，则说明当前服务器可用内存无法支撑预设的应用运行时间目标。

如果吞吐量目标可以满足，但 GC 停顿时间过长，可配置最大停顿时间目标。设置最大停顿时间通常会牺牲部分吞吐量，需选择业务可接受的折中参数。

垃圾回收器在协调多个相互冲突的目标时，堆内存大小往往会出现震荡波动；即便应用已进入稳态运行，该现象也依然存在。

吞吐量目标倾向于更大堆内存，而最大停顿时间目标、最小内存占用目标则倾向于更小堆内存，三者互相制衡、存在取舍关系。

3 垃圾回收器实现

Java SE 平台的一大优势，是为开发者屏蔽了内存分配与垃圾回收的底层复杂细节。

但当垃圾回收成为系统主要性能瓶颈时，了解其部分底层实现原理就很有必要。垃圾回收器会对应用程序的对象使用模式做出预设假设，这些假设体现在各类可调优参数中。开发者可通过调整参数优化运行性能，同时无需牺牲抽象机制带来的设计优势。

分代垃圾回收

当运行程序中任何存活对象都无法再通过引用访问到某个对象时，该对象就会被判定为垃圾，其占用的内存可由虚拟机回收复用。

有一种理论上最简单直观的垃圾回收算法：每次执行回收时，遍历堆中所有可达对象，剩余未被遍历到的对象即判定为垃圾。该算法的执行耗时与存活对象数量成正比，对于需要常驻大量存活数据的大型应用来说，这种方案开销过大、难以采用。

Java HotSpot 虚拟机提供了多种垃圾回收算法，除 ZGC 以外，其余所有收集器均采用分代回收技术。普通基础垃圾回收每次都需要扫描堆内全部存活对象，而分代回收依托绝大多数应用程序呈现出的若干经验特征，最大程度减少回收废弃垃圾对象的工作量。其中最重要的特征就是弱分代假说：绝大多数对象都仅存活很短的时间。

图 3-1 中的蓝色区域展示了对象生命周期的典型分布特征。横轴为以内存分配字节数度量的对象生命周期；纵轴字节数代表对应生命周期区间内所有对象占用的总内存字节数。左侧陡峭的峰值代表这类对象在分配后很快就能被回收（即快速消亡）。例如迭代器对象，通常仅在单次循环的执行周期内存活。

也有部分对象拥有较长的生命周期，因此该分布曲线向右侧延伸。例如，应用在初始化阶段分配的部分对象，其生命周期会一直延续到虚拟机退出。在这两种极端情况之间，还存在一批生命周期与中间计算过程一致的对象，对应图中初始峰值右侧的隆起区域。少数应用的对象生命周期分布形态会有所差异，但绝大多数应用都呈现这种整体分布特征。正是依托绝大多数对象朝生夕灭这一特点，才得以实现高效的垃圾回收。

分代

为适配上述对象生命周期特征，虚拟机将内存按分代进行管理（分代即存放不同年龄对象的内存池）。当某个分代内存占满时，便会触发该分代的垃圾回收。

绝大多数对象都分配在专门存放年轻对象的内存区域，也就是新生代，并且大部分对象都在新生代消亡。当新生代空间耗尽时，会触发Minor GC，仅对新生代执行回收，不处理其他分代的垃圾。这类回收的开销大体上与存活对象数量成正比；若新生代中大多对象已消亡，回收速度会非常快。每次 Minor GC 过后，新生代中存活的部分对象会晋升至老年代。最终老年代空间也会被占满，需要执行回收，进而触发Major GC，对整个堆内存进行全量回收。Major GC 的耗时通常远高于 Minor GC，因为需要处理的对象规模大得多。图 3-2 展示了串行垃圾回收器中默认的分代内存布局。

虚拟机启动时，Java HotSpot 会在进程地址空间中完整预留整个 Java 堆，但并不会立刻分配物理内存，仅在实际需要时才进行物理内存分配。Java 堆对应的整片地址空间，在逻辑上被划分为新生代与老年代。为对象内存预留的全部地址空间，均可划分为新生代和老年代两部分。

新生代由伊甸区（Eden） 和两个幸存者区（Survivor Space） 组成。绝大多数对象初始都在伊甸区分配。任意时刻，两个幸存者区中总有一个处于空闲状态；垃圾回收时，伊甸区以及另一个非空闲幸存者区中的存活对象，都会复制到这个空闲幸存者区。回收结束后，伊甸区和作为数据源的幸存者区将被清空。下一次垃圾回收时，两个幸存者区的角色相互交换。上一轮刚被填满的幸存者区作为存活对象源，对象被复制到另一个幸存者区。对象以这种方式在两个幸存者区之间往复复制，直到复制次数达到指定阈值，或是幸存者区剩余空间不足。这时这些对象会被复制到老年代区域，该过程也称作年龄晋升。

性能考量

垃圾回收的核心衡量指标为吞吐量和延迟。

  • 吞吐量：长期运行周期内，应用总耗时中扣除垃圾回收耗时的占比。吞吐量统计包含对象内存分配耗时（通常无需专门针对内存分配速率进行调优）。
  • 延迟：指应用程序的响应能力。垃圾回收停顿会直接影响应用的响应表现。

不同业务场景对垃圾回收有着差异化需求。例如，Web 服务器一般以吞吐量作为核心衡量标准，因为 GC 停顿通常可以容忍，或是会被网络延迟所掩盖。但在交互式图形应用中，即便是短暂的 GC 停顿，也会严重损害用户体验。

部分业务还会关注其他评估维度。内存占用指进程的工作集，以内存页、缓存行为度量单位。在物理内存有限或进程数量繁多的系统中，内存占用会直接决定系统可扩展性。回收及时性是从对象变为无效垃圾，到其占用内存变为可用状态的间隔时长。该指标对分布式系统（包括远程方法调用 RMI）尤为重要。

总体来说，设置各分代内存大小，需要在以上各项指标之间做权衡取舍。例如，超大新生代可以最大化吞吐量，但会牺牲内存占用、回收及时性与停顿时间；缩小新生代可最大限度降低新生代 GC 停顿耗时，代价是吞吐量下降。一个分代的容量设置，不会影响另一个分代的回收频率和停顿时长。

分代内存大小没有通用的最优配置。最佳方案取决于应用的内存使用特征以及业务诉求。因此虚拟机默认选用的垃圾回收器未必适配所有场景，开发者可通过命令行参数手动覆盖默认配置；详见《影响垃圾回收性能的因素》章节。

4 影响垃圾回收性能的因素

影响垃圾回收性能最重要的两大因素：系统可用总内存，以及堆内存分配给新生代的占比。

总堆内存

影响垃圾回收性能最关键的因素是可用总内存。由于分代空间填满时就会触发垃圾回收，因此吞吐量与可用内存大小成反比。

下文关于堆的扩容与收缩、堆内存布局以及默认参数值的相关讲解，均以串行垃圾回收器为例。其他垃圾回收器虽采用类似机制，但本文所述细节不一定适用于其他收集器。如需了解其他收集器的同类内容，请查阅对应专题说明。

影响分代大小的堆参数选项

有多项虚拟机参数可控制各分代的内存大小。图 4-1 展示了堆中已提交空间与虚拟空间的区别。虚拟机初始化时，会预先预留完整的堆地址空间，可通过 -Xmx 参数设定该预留空间的最大值。若 -Xms 参数值小于 -Xmx，则已预留的地址空间不会一次性全部向虚拟机提交物理内存。图中将这类未提交的空间标注为虚拟空间。堆的各个组成区域（老年代、新生代）可根据运行需求，扩容至虚拟空间的上限。

还有部分参数用于设定堆各区域间的内存比例。例如 -XX:NewRatio 参数，用于定义老年代相对新生代的内存大小比例。

堆大小的默认参数值

默认情况下，虚拟机每次垃圾回收时都会对堆进行扩容或收缩，力求把每次回收后空闲空间与存活对象的占比维持在特定区间内。

可通过参数 -XX:MinHeapFreeRatio=<最小值> 和 -XX:MaxHeapFreeRatio=<最大值> 以百分比形式设定该目标区间；堆总大小的下限由 -Xms<最小值> 限定，上限由 -Xmx<最大值> 限定。

基于这些参数规则：若某个分代的空闲空间占比低于 40%，该分代会触发扩容，将空闲空间维持在 40%，扩容上限不超过分代最大允许容量。同理，若空闲空间占比超过 70%，该分代会主动收缩，把空闲空间占比降至 70%，且收缩后不能低于分代最小容量。

Java SE 中原先为并行回收器设计的堆大小计算逻辑，目前已适用于所有垃圾回收器。该计算规则包含 64 位平台下最大堆内存的上限约束，详情参见并行回收器默认堆大小。客户端虚拟机也采用一套类似计算规则，其最终最大堆容量通常小于服务端虚拟机。

以下是服务端应用堆内存配置的通用准则：

  • 若无 GC 停顿相关问题，尽量为虚拟机分配充足内存，官方默认堆大小通常偏小。
  • 将 -Xms 和 -Xmx 设为相同值，可剥夺虚拟机自主调堆的权限，提升运行行为的可预测性。但弊端是：若配置不合理，虚拟机无法自动动态补偿调整。
  • 一般而言，处理器核心数越多，配置的堆内存也应相应加大，因为对象内存分配支持并行执行。

通过最小化 Java 堆大小来降低动态内存占用

如果需要最小化应用程序的动态内存占用（运行期间消耗的最大物理内存），可以通过减小 Java 堆大小实现。Java SE 嵌入式应用通常有这类需求。

通过降低以下两个参数的值来最小化 Java 堆大小：-XX:MaxHeapFreeRatio（默认值 70%）和-XX:MinHeapFreeRatio（默认值 40%）。实践证明：将 -XX:MaxHeapFreeRatio 降至 10%，同时降低 -XX:MinHeapFreeRatio，可以在性能损失不大的前提下有效减小堆大小。但效果会因应用类型差异很大，建议不断尝试调整参数，在保证可接受性能的前提下尽可能降低数值。

在串行 GC 中，可以使用 -XX:-ShrinkHeapInSteps 参数，让虚拟机立即将堆收缩到目标大小（由 -XX:MaxHeapFreeRatio 指定）。该配置可能导致性能下降。如果不启用该参数，Java 运行时会通过多次垃圾回收周期，逐步渐进式收缩堆。

新生代

在可用总内存之后，影响垃圾回收性能的第二大关键因素，是堆内存中分配给新生代的占比。

新生代越大，Minor GC 的触发频率就越低。但在堆总大小固定的前提下，新生代越大就意味着老年代越小，进而会提高 Major GC 的触发频次。最优配置取决于应用对象生命周期的分布特征。

新生代大小配置参数

默认情况下，新生代大小由参数 -XX:NewRatio控制。

例如，设置 -XX:NewRatio=3 表示新生代与老年代的大小比例为 1:3。换句话说：伊甸区（Eden）+ 两个幸存者区（Survivor）的总大小 = 堆总大小的 1/4。

参数 -XX:NewSize 和 -XX:MaxNewSize 分别限定了新生代的最小值和最大值。将这两个参数设置为相同的值，就可以固定新生代大小，就像把 -Xms 和 -Xmx 设为相同值来固定整个堆大小一样。相比于只能按整数比例调整的 -XX:NewRatio，这种方式可以实现更细粒度的新生代调优。

幸存者区大小设置

可以通过 -XX:SurvivorRatio 参数调整幸存者区大小，但该参数通常对整体性能影响不大。

例如，配置 -XX:SurvivorRatio=6，表示单个幸存者区与伊甸区的比例为 1:6。换言之：每个幸存者区容量为伊甸区的 1/6；由于新生代包含一个伊甸区和两个幸存者区，因此单个幸存者区占新生代总容量的 1/8（而非 1/7）。

若幸存者区过小，复制回收时存活对象会直接溢出晋升到老年代；若幸存者区过大，则会长期闲置、浪费空间。每次垃圾回收时，虚拟机都会动态计算一个晋升阈值：代表对象在幸存者区之间复制多少次后，将被判定为老对象并晋升到老年代。该阈值的设计目标是让幸存者区始终保持半满状态。可通过日志参数 -Xlog:gc,age 打印该晋升阈值，以及新生代中所有对象的年龄分布，也可用于观测应用的对象生命周期分布特征。

配置 默认参数值

-XX:NewSize 1310 MB

新生代的最大容量由堆最大总容量与 -XX:NewRatio 参数共同计算得出。-XX:MaxNewSize 默认取值为无限制，意味着除非在命令行手动指定该参数，否则新生代最大容量不受 -XX:MaxNewSize 约束，完全按公式自动计算。

以下是服务端应用的通用调优准则：

  • 首先确定服务器可分配给虚拟机的最大堆内存；再以新生代不同容量为变量，观测性能指标变化，找出最优配置。
    • 需注意：最大堆内存务必小于机器物理内存总量，避免产生过多页缺页异常与系统颠簸。
  • 若堆总大小固定，调大新生代就必须缩减老年代。应保证老年代容量足够容纳应用任意时刻的全部存活数据，并预留10%~20% 及以上的富余缓冲空间。
  • 在满足上述老年代容量约束的前提下，遵循以下原则：
    • 尽量给新生代分配充足内存；
    • 处理器核心数越多，越应调大新生代容量，因为对象分配支持并行化执行。

5 可用的垃圾回收器

至此为止的讲解均围绕串行垃圾回收器展开。Java HotSpot 虚拟机内置三种不同类型的垃圾回收器，每一种都具备各异的性能特性。

串行垃圾回收器

串行回收器采用单线程完成所有垃圾回收工作。由于不存在多线程间的通信开销，因此执行效率相对较高。

该回收器最适用于单处理器设备，无法发挥多处理器硬件的优势；但在多处理器环境中，对于数据集较小（约 100MB 以内）的应用，串行回收器也依然适用。在特定硬件与操作系统组合下，虚拟机默认会选用串行回收器；也可通过命令行参数-XX:+UseSerialGC手动显式启用。

并行垃圾回收器

并行回收器也称作吞吐量回收器，它与串行回收器一样，都属于分代式回收器。二者最核心的区别是：并行回收器依靠多线程执行垃圾回收，以此提升回收效率。

并行回收器适用于部署在多处理器、多线程硬件环境，且承载中大型数据集的应用。可通过参数 -XX:+UseParallelGC 手动启用。

并行整理 是并行回收器的一项特性，支持以多线程方式执行老年代全量回收。若不开启并行整理，老年代回收只能单线程运行，会严重制约系统可扩展性。当配置-XX:+UseParallelGC 时，并行整理默认自动启用；可通过 -XX:-UseParallelOldGC 参数将其关闭。

G1（Garbage-First）垃圾回收器

G1 是一款近乎并发的垃圾回收器。这类回收器会将部分耗时较高的回收任务，与应用业务线程并发执行。G1 的设计具备优秀的伸缩能力，可适配从小型设备，到大内存、多处理器的大型服务器环境。它既能高概率达成预设的停顿时间目标，又能保持较高的吞吐量。

在绝大多数硬件与操作系统环境中，G1 是默认选用的垃圾回收器；也可通过参数 -XX:+UseG1GC 手动显式启用。

Z 垃圾回收器（ZGC）

ZGC 是一款可伸缩的低延迟垃圾回收器。ZGC 把所有耗时的回收工作都进行并发处理，全程无需暂停应用线程的运行。

ZGC 的最大停顿时间仅为数毫秒级别，代价是会小幅牺牲部分吞吐量。它专为低延迟需求的应用设计，且停顿时间与堆内存大小无关。ZGC 支持的堆内存范围从 8MB 到 16TB。可通过 -XX:+UseZGC 参数启用该回收器。

垃圾回收器的选择

除非应用对停顿时间有严苛要求，否则可先直接运行应用，由虚拟机自动选择合适的垃圾回收器。

如有需要，可先调整堆内存大小来优化性能；若性能仍达不到预期，可参照以下准则作为选择回收器的初始依据：

  • 若应用属于小数据集（约 100MB 以内），使用 -XX:+UseSerialGC 选用串行回收器。
  • 若应用运行在单处理器环境，且无停顿时间要求，使用 -XX:+UseSerialGC 选用串行回收器。
  • 若满足以下两点：(a) 应用峰值性能为首要目标；(b) 无停顿时间约束，或可接受一秒及以上的 GC 停顿；则可由虚拟机自动选择，或通过-XX:+UseParallelGC手动选用并行回收器。
  • 若响应时间比整体吞吐量更重要，且必须严格控制 GC 停顿时长，通过 -XX:+UseG1GC 选用近乎并发的 G1 回收器。
  • 若高度看重响应时间，可通过 -XX:+UseZGC 选用完全并发的 ZGC 回收器。

以上准则仅作为选型参考起点。实际性能还取决于堆大小、应用常驻的存活数据量，以及可用处理器的数量与主频。

若推荐的回收器无法达到预期性能，应先尝试调整堆和各分代大小以满足性能目标；若效果依旧不佳，再更换其他回收器：追求低停顿选并发回收器，多处理器环境下追求高整体吞吐量则选用并行回收器。

6 并行垃圾回收器

并行回收器（本文中也称作吞吐量回收器）是一款分代式垃圾回收器，与串行回收器特性相似。串行回收器和并行回收器的核心区别在于：并行回收器使用多线程执行垃圾回收，以此加速回收过程。

可通过命令行参数 -XX:+UseParallelGC 启用并行回收器。在默认配置下，启用该参数后，新生代回收（Minor GC）和老年代回收（Major GC）均采用多线程并行执行，从而进一步降低垃圾回收的性能开销。

并行回收器的垃圾回收线程数

在拥有 <N> 个硬件线程的服务器上，若 N 大于 8，并行回收器会采用 N 的固定比例作为垃圾回收线程数。

当 N 取值较大时，该比例约为 5/8；若 N 小于等于 8，回收线程数等于硬件线程数 N；在部分特定平台中，该比例会降至 5/16。垃圾回收线程的具体数量可通过命令行参数调整（后续章节会详细说明）。在单处理器主机上，由于并行执行带来的额外开销（如线程同步），并行回收器的性能通常不如串行回收器。但在双处理器设备上运行中大型堆的应用时，并行回收器的性能会小幅优于串行回收器；当处理器数量超过 2 个时，其性能会显著超越串行回收器。

可通过命令行参数 -XX:ParallelGCThreads=<N> 手动指定垃圾回收线程数。如果通过命令行参数调优堆内存，并行回收器实现良好性能所需的堆大小，与串行回收器一致。但启用并行回收器能有效缩短回收停顿时间。由于多线程协同执行新生代回收，回收过程中对象从新生代向老年代的晋升操作可能会产生内存碎片。参与新生代回收的每个 GC 线程，都会在老年代中预留一部分空间用于对象晋升，可用内存被分割为这些晋升缓冲区，最终导致内存碎片问题。减少 GC 线程数、增大老年代容量，可以缓解这种内存碎片现象。

通过 -XX:+UseParallelGC 启用并行回收器时，会自动开启自适应调优机制。该机制允许开发者只指定期望的运行行为，而无需手动配置分代大小以及其他底层调优细节。

并行回收器行为配置参数

你可以为并行回收器指定三项运行指标：最大垃圾回收停顿时间、吞吐量以及内存占用（堆大小）。

  • 最大垃圾回收停顿时间：可通过命令行参数 -XX:MaxGCPauseMillis=<N> 设定最大 GC 停顿时间目标。该参数作为一种期望值建议，希望 GC 停顿时间控制在 N 毫秒及以内；默认情况下不设置最大停顿时间目标。一旦指定停顿时间目标，虚拟机将自动调整堆大小及其他 GC 相关参数，尽力把 GC 停顿控制在设定值之内，但无法保证一定能达成目标。这类自适应调整，有可能会降低应用的整体吞吐量。

  • 吞吐量：吞吐量以垃圾回收耗时与应用业务运行耗时的占比来衡量，其中非 GC 的运行时段称为应用运行时间。通过命令行参数 -XX:GCTimeRatio=<N> 设定期望吞吐量目标，它将GC 耗时与应用耗时的比例设定为：$\boldsymbol{1/1+}$。

    例如配置 -XX:GCTimeRatio=19，代表目标为总运行时间中有 1/20（5%）用于垃圾回收。

    该参数默认值为 99，对应 GC 耗时占比目标为 1%。

  • 内存占用：最大堆内存占用由 -Xmx<N> 参数指定。除此之外，在满足停顿时间、吞吐量两大目标的前提下，回收器还有一个隐性目标：尽可能压缩堆内存占用。

回收器会在每次垃圾回收结束后，更新平均停顿时间等统计指标。

分代的扩容与缩容，均按照自身当前容量的固定百分比步进，逐步向理想容量靠拢。扩容和缩容的步进速率并不相同：默认规则为，分代每次扩容 20%，每次缩容 5%。新生代的扩容百分比由参数 -XX:YoungGenerationSizeIncrement=<Y> 控制，老年代扩容百分比由 -XX:TenuredGenerationSizeIncrement=<T> 控制。分代缩容比例可通过 -XX:AdaptiveSizeDecrementScaleFactor=<D> 调整：若扩容步进为 X%，则缩容步进为 $\boldsymbol{X/D\%}$。

若回收器在应用启动阶段需要扩容分代，会在基础扩容比例上额外叠加一个补偿比例。该补偿值会随着 GC 次数增多逐步衰减，无长期影响，设计初衷是提升应用启动性能。缩容操作不设置任何额外补偿比例。

若无法满足最大停顿时间目标，每次仅缩容一个分代。如果新生代、老年代的 GC 停顿均超出目标阈值，则优先缩容停顿耗时更长的那个分代。

若无法达成吞吐量目标，会同时扩容新生代与老年代。每个分代的扩容幅度，按其 GC 耗时占总 GC 耗时的权重比例分配。举例说明：新生代 GC 耗时占全局 GC 总耗时的 25%，新生代默认完整扩容幅度为 20%，则本次新生代实际扩容幅度为 5%。

并行回收器默认堆大小

如果没有在命令行手动指定初始堆大小和最大堆大小，虚拟机将根据机器物理内存容量自动计算这两个值。默认最大堆大小为物理内存的 1/4，初始堆大小为物理内存的 1/64。新生代可分配的最大空间为堆总容量的 1/3。

7 垃圾优先（G1）垃圾回收器

本节将介绍垃圾优先（G1）垃圾回收器（GC）。

垃圾优先（G1）垃圾回收器简介

垃圾优先（G1）垃圾回收器面向多处理器设备设计，可平滑扩展至大内存环境。它能够高概率达成预设的 GC 停顿时间目标，同时维持高吞吐量，且几乎无需人工复杂配置。

对于当下主流应用及运行环境，G1 致力于在延迟与吞吐量之间实现最佳平衡，这类场景通常具备以下特点：

  • 堆内存可达数十 GB 甚至更大，且 Java 堆中存活数据占比超过 50%；
  • 对象分配速率与对象晋升速率会随时间发生大幅波动；
  • 堆内存存在严重的内存碎片；
  • 要求停顿时间可预测、控制在数百毫秒以内，避免出现长时间 GC 停顿。

G1 会将部分垃圾回收工作与应用业务并发执行。它牺牲一部分原本可供给应用使用的处理器资源，以此换取更短的回收停顿。

最直观的体现是：应用运行过程中，会有一个或多个 GC 线程持续后台工作。因此，相较于吞吐量回收器，G1 的 GC 停顿通常短得多，但应用整体吞吐量会略微降低。

G1 是 JVM 默认的垃圾回收器。

后续章节将介绍 G1 实现高性能、并尽力满足停顿时间目标的多种核心机制。

启用 G1

垃圾优先（G1）垃圾回收器是默认垃圾回收器，因此通常无需进行额外配置。你可以在命令行添加 -XX:+UseG1GC 参数，显式启用 G1 回收器。

基本概念

G1 是一款兼具分代、增量、并行、近乎并发、全局停顿、拷贝疏散特性的垃圾回收器，会在每次全局停顿阶段监控停顿时间目标。与其他回收器类似，G1 将堆内存划分为逻辑上的新生代与老年代。内存回收工作优先聚焦在回收效率最高的新生代，同时也会不定期对老年代执行内存回收。

部分操作必须在全局停顿中执行，以此保障吞吐量。其余若停止应用线程执行会耗时过久的操作（如全局标记这类全堆扫描操作），则与应用线程并行、并发运行。为把内存回收的全局停顿控制在较短水平，G1 采用分步增量 + 多线程并行的方式完成回收。G1 会统计应用历史运行特征与历次 GC 停顿数据，构建开销预估模型，以此实现停顿时间的可预测性，并根据模型控制每次停顿内的回收工作量。例如，G1 优先回收收益最高的内存区域（垃圾占比最高的分区），这也是其垃圾优先命名的由来。

G1 主要依靠拷贝疏散完成内存回收：挑选待回收的内存分区，将分区内的存活对象复制到新的内存区域，同时完成内存整理压缩。疏散完成后，原对象占用的内存空间被释放，可重新交由应用用于对象分配。

G1 不属于实时垃圾回收器。它能在长期运行中高概率达成设定的停顿时间目标，但无法保证单次 GC 停顿绝对满足指标。

堆内存布局

G1 将堆内存划分成若干大小均等的堆分区，每个分区都是一段连续的虚拟内存空间，如图 7-1 所示。分区是 G1 内存分配和内存回收的基本单位。在任意时刻，每个分区可以是空闲状态（浅灰色），也可以被分配给新生代或老年代中的某一个分代。当应用发起内存申请时，内存管理器会分配空闲分区。内存管理器先将这些分区划归至某个分代，再作为空闲空间提供给应用，供应用在其中进行对象内存分配。

新生代包含伊甸分区（红色）和存活区分区（带标识 S 的红色分区）。这些分区的功能与其他回收器中对应的连续内存空间完全一致，区别在于：G1 的这些分区在内存中通常以非连续形式排布。老年代分区（浅蓝色）组成老年代。针对占用多个分区的大对象，老年代还设有巨型分区（带标识 H 的浅蓝色分区）专门存放。

应用常规对象始终分配在新生代的伊甸分区；巨型对象是特例，会直接分配归属到老年代。

垃圾回收周期

从宏观层面来讲，G1 回收器会在两个阶段之间交替运行。仅新生代阶段的垃圾回收会不断分配对象、占用可用内存，并逐步扩充老年代的内存占用。空间回收阶段除了常规处理新生代回收之外，G1 还会以增量方式回收老年代的内存空间。本轮周期结束后，会重新回到仅新生代阶段，开启下一轮循环。

下文详细阐述 G1 垃圾回收周期的各个阶段、对应STW 停顿以及阶段间的切换机制：

  1. 仅新生代阶段：该阶段以多次普通新生代 GC开启，持续将对象晋升到老年代。当老年代内存占用达到指定阈值，即堆占用启动阈值（IHOP） 时，仅新生代阶段开始向空间回收阶段切换。此时 G1 不再执行普通新生代 GC，而是触发并发启动新生代 GC。
    • 并发启动阶段：这类 GC 在完成常规新生代回收的同时，会启动并发标记流程。并发标记会遍历识别老年代分区中所有当前可达（存活） 对象，为后续空间回收阶段划定需保留的存活对象。在并发标记未完全结束期间，依然可以执行普通新生代 GC。标记流程最终由两个专属全局停顿（STW） 收尾：重新标记（Remark） 和 清理（Cleanup）。
    • 重新标记（Remark）：该停顿完成标记流程的收尾工作，执行全局引用处理与类卸载，回收完全空闲的堆分区，并清理内部数据结构。在重新标记与清理停顿之间，G1 会提前计算相关统计信息，用于后续并发回收指定老年代分区的空闲空间，相关计算结果将在清理停顿中做最终确认。
    • 清理（Cleanup）：该停顿会判定后续是否正式进入空间回收阶段。若确定开启空间回收阶段，则仅新生代阶段会以一次混合准备新生代 GC作为收尾。
  2. 空间回收阶段：该阶段包含多次混合 GC。混合 GC 除了处理新生代分区的回收外，还会对一批老年代分区中的存活对象执行拷贝疏散。当 G1 判断继续疏散更多老年代分区、所能释放的空闲空间得不偿失时，空间回收阶段就此结束。

空间回收阶段结束后，垃圾回收周期会重新进入新一轮仅新生代阶段。作为兜底保障机制：倘若 JVM 在存活对象信息标记过程中，应用发生内存耗尽，G1 会和其他回收器一样，触发全局停顿式全堆原位整理 Full GC。

垃圾回收停顿与收集集合

G1 在全局停顿（STW） 阶段执行垃圾回收与内存空间回收。流程通常是将存活对象从源分区复制到堆内一个或多个目标分区，同时修正所有指向这些已迁移对象的引用。

对于非巨型分区，对象的目标分区由其所在源分区的类型决定：

  • 新生代对象（伊甸分区、存活区分区）根据对象年龄，被复制到存活区分区或老年代分区；
  • 老年代分区中的对象，会拷贝至其他老年代分区。

巨型分区的对象采用特殊处理逻辑：G1 仅判定其中对象的存活状态，若对象已消亡，则回收其占用内存；巨型分区内的对象永远不会被 G1 移动或拷贝。

收集集合 是所有待执行空间回收的源分区合集。根据垃圾回收类型不同，收集集合包含的分区类型也有区别：

  • 仅新生代阶段：收集集合只包含新生代分区，以及存有可回收对象的巨型分区；
  • 空间回收阶段：收集集合包含新生代分区、存有可回收对象的巨型分区，以及收集集合候选分区中的部分老年代分区。

G1 在并发运行周期中提前准备收集集合候选分区。在重新标记（Remark） 停顿期间，G1 筛选出内存占用率低的分区（即空闲空间占比高的分区）。在重新标记与清理（Cleanup）两个停顿之间，G1 以并发方式对这些分区做预处理，为后续回收做好准备。清理停顿会按照回收效率对预处理结果排序：后续混合 GC 会优先选择回收耗时短、可释放空闲空间多的高性价比分区进行回收。

G1 内部原理

本节介绍垃圾优先（G1）垃圾回收器的若干重要底层细节。

Java 堆大小调整

G1 调整 Java 堆容量时遵循标准规则：以 -XX:InitialHeapSize 作为 Java 堆最小初始大小；以 -XX:MaxHeapSize 作为 Java 堆最大上限；-XX:MinHeapFreeRatio 控制堆空闲内存的最小占比；-XX:MaxHeapFreeRatio 用于限定堆扩容完成后空闲内存的最大占比。G1 仅在重新标记停顿与 Full GC 停顿期间 才会触发堆大小调整。该过程可以向操作系统释放空闲内存，也可向操作系统申请分配额外内存。

仅新生代阶段的分代大小调整

G1 总会在普通新生代垃圾回收结束时，为下一个应用业务运行阶段重新核算并设定新生代大小。G1 基于对历史实际停顿耗时的长期统计，以此匹配由 -XX:MaxGCPauseTimeMillis 和 -XX:PauseTimeIntervalMillis 设定的停顿时间目标。它会参考过往同等容量新生代执行拷贝疏散的耗时情况，同时综合回收时需拷贝的对象数量、对象间引用关联复杂度等维度信息。

若无其他参数强制约束，G1 会在 -XX:G1NewSizePercent 与 -XX:G1MaxNewSizePercent 限定的区间内，自适应调整新生代容量，力求满足停顿时间指标。如需解决 GC 长停顿问题，可查阅G1 垃圾回收器调优Garbage-First Garbage Collector Tuning相关资料。

也可通过组合配置 -XX:NewSize 和 -XX:MaxNewSize，分别手动设定新生代的最小容量与最大容量。

若仅单独配置 -XX:NewSize 与 -XX:MaxNewSize 中的任意一个参数，新生代大小会被直接固定为该参数设定的具体数值。

空间回收阶段的分代容量调整

在空间回收阶段，G1 会尽可能在单次 GC 停顿中最大化老年代的内存回收量。此时新生代大小会被设定为允许的最小值，该值通常由参数 -XX:G1NewSizePercent 决定。

本阶段每一次混合 GC 开始时，G1 都会从收集集合候选分区中选取一批分区，纳入本次收集集合。这批新增的老年代分区由三部分构成：

  • 保底老年代分区集合：用于保障内存疏散进度。该分区数量计算方式为：收集集合候选分区总数，除以由 -XX:G1MixedGCCountTarget 设定的空间回收阶段总混合 GC 轮次。
  • 追加老年代分区集合：若 G1 预估完成保底分区回收后仍有剩余停顿时间，则继续从候选分区中追加老年代分区；持续新增直至预估耗时占用剩余停顿时长的 80% 为止。
  • 可选收集集合分区：在前两类分区完成疏散后，若本次停顿仍有剩余时间，G1 会增量式疏散这部分可选分区。

前两类分区会在首轮回收流程中统一处理，可选分区则根据剩余停顿时间见缝插针执行回收。该机制既能保证内存回收进度，又能提升停顿时间达标概率，同时将可选分区调度带来的开销控制在最低水平。

当收集集合候选分区中剩余可回收空间占比低于 -XX:G1HeapWastePercent 设定的阈值时，空间回收阶段正式结束。

如需了解 G1 选取老年代分区的具体规则、以及如何避免混合 GC 长停顿问题，可参考G1 垃圾回收器调优Garbage-First Garbage Collector Tuning相关文档。

周期性垃圾回收

如果因应用长期空闲而长时间没有触发垃圾回收，虚拟机可能会持续占用大量闲置内存，无法释放出来供其他场景使用。为避免该问题，可通过 -XX:G1PeriodicGCInterval 参数强制 G1 执行周期性垃圾回收。该参数以毫秒为单位，设定 G1 触发 GC 的最小时间间隔。只要距离上一次 GC 停顿超过该时长，且当前没有正在执行的并发周期，G1 就会主动触发额外垃圾回收，产生如下效果：

  • 处于仅新生代阶段：G1 会通过并发启动停顿开启并发标记；若配置了 -XX:-G1PeriodicGCInvokesConcurrent，则直接触发 Full GC。
  • 处于空间回收阶段：G1 延续当前空间回收流程，触发与当前回收进度相匹配的 GC 停顿类型。

-XX:G1PeriodicGCSystemLoadThreshold 参数可精细化控制是否触发周期 GC：JVM 所在主机（包括容器）通过系统 getloadavg() 接口获取1 分钟平均系统负载，若负载超过该阈值，则不会执行周期性垃圾回收。

关于周期性垃圾回收的更多细节，可参考 JEP 346: Promptly Return Unused Committed Memory from G1 （G1 及时归还未使用的已提交内存）。

堆占用启动阈值（IHOP）的计算

堆占用启动百分比（IHOP） 是触发初始标记 GC的阈值，该阈值以老年代容量占比的形式定义。

G1 默认会通过观测并发标记耗时、以及标记周期内老年代的常规内存分配速率，自动计算出最优 IHOP 值，该机制称为自适应 IHOP。当自适应 IHOP 生效、且暂无充足历史观测数据无法精准预测阈值时，JVM 会采用 -XX:InitiatingHeapOccupancyPercent 作为初始阈值，按当前老年代大小的百分比进行设定。可通过参数 -XX:-G1UseAdaptiveIHOP 关闭 G1 的自适应 IHOP 特性；关闭后，将固定由 -XX:InitiatingHeapOccupancyPercent 唯一决定堆占用启动阈值。

在底层实现上，自适应 IHOP 的调控目标为：让空间回收阶段的第一轮混合 GC启动时，老年代内存占用量恰好等于当前老年代最大容量扣除 -XX:G1HeapReservePercent 所预留的内存缓冲值。

标记阶段

G1 标记采用起始快照算法（SATB, Snapshot-At-The-Beginning）。算法会在初始标记停顿时刻，对堆生成一份逻辑快照：标记起始时所有存活的对象，在整个后续标记流程中均被判定为存活对象。这意味着，标记过程中变为不可达的死亡对象，在本轮空间回收中仍会被视作存活对象（存在少数例外情况）。相较于其他回收器，SATB 会导致部分内存被保守滞留、无法及时回收。但该算法可以显著优化重新标记停顿的延迟表现。本轮标记中被过度保守判定为存活的对象，将在下一轮标记周期中被回收。如需了解标记阶段常见问题及排查方案，可查阅G1 垃圾回收器调优Garbage-First Garbage Collector Tuning相关内容。

堆内存极度紧张场景下的运行表现

当应用存活对象占用内存过大，致使拷贝疏散流程找不到足够内存空间作为对象复制目标时，就会发生疏散失败。出现疏散失败时，G1 会尝试以特殊方式完成当前垃圾回收：已迁移完毕的对象保留在新内存位置，不再拷贝尚未迁移的对象，仅修正对象之间的引用关系。疏散失败会产生一定额外开销，但整体执行速度通常与普通新生代垃圾回收相近。发生疏散失败的 GC 执行完毕后，G1 会直接恢复应用正常运行，无需额外采取其他处理措施。G1 隐含一个前提假设：疏散失败一般发生在垃圾回收临近结束时，此时绝大部分对象已完成迁移，剩余内存足以支撑应用持续运行，直至并发标记完成并进入空间回收阶段。

若上述假设不成立，G1 最终会调度触发 Full GC。该类型 GC 会对整个堆进行原位内存整理，执行耗时往往会非常漫长。

如需了解内存分配失败、OOM 触发前频繁 Full GC 等问题的排查与优化，可参阅G1 垃圾回收器调优Garbage-First Garbage Collector Tuning相关资料。

巨型对象

巨型对象指大小大于等于半个分区容量的对象。除非通过 -XX:G1HeapRegionSize 参数手动指定分区大小，否则当前分区大小会按照《G1 GC 自适应默认配置》章节所述，由 JVM自适应计算确定。

这类巨型对象会采用特殊的处理规则：

  • 所有巨型对象均在老年代中分配一段连续的分区序列进行存储。对象的起始地址必须对齐到该序列首个分区的起始位置。序列最后一个分区中未被使用的剩余空间，会被闲置无法分配，直到该巨型对象被整体回收。
  • 常规情况下，巨型对象仅能在清理停顿的标记收尾阶段被回收；若对象变为不可达状态，也可在 Full GC 时回收。但针对基本类型数组（如布尔型、各类整型、浮点型数组）这类巨型对象存在特殊优化：在任意 GC 停顿阶段，若这类对象未被大量对象引用，G1 会主动尝试回收。该特性默认开启，可通过参数 -XX:G1EagerReclaimHumongousObjects 关闭。
  • 分配巨型对象可能提前触发 GC 停顿。G1 在每次分配巨型对象时，都会校验堆占用启动阈值（IHOP）；若当前老年代内存占用量超过该阈值，会立即强制触发初始标记新生代 GC。
  • 巨型对象永远不会被移动，即便在 Full GC 期间也不例外。这会因分区空间碎片化，导致提前触发耗时极长的 Full GC，或堆内仍有大量空闲空间却意外触发内存溢出（OOM）。

G1 GC 自适应默认配置

本章概述 G1 垃圾回收器专属的核心默认配置项及其默认值。通过这些配置，可大致了解不额外添加任何参数时，G1 的预期运行行为与资源占用情况。

配置及默认值 说明
-XX:MaxGCPauseMillis=200 设定最大 GC 停顿时间目标为 200 毫秒。
-XX:GCPauseTimeInterval= 指定GC 停顿时间间隔目标。默认情况下 G1 不设置任何间隔限制，极端场景中允许 G1 连续不间断地执行垃圾回收。
-XX:ParallelGCThreads= 垃圾回收停顿阶段执行并行工作的最大线程数。该参数值由 JVM 运行主机的可用线程数按以下规则自适应计算：若进程可使用的 CPU 线程数 ≤ 8，则直接采用该数值；若线程数 ＞ 8，则最终线程数 = 8 + (超出 8 的线程数 × 5/8)。
在每次 GC 停顿开始时，实际使用的最大线程数还会受到堆总容量的额外限制：Java 堆容量每对应 -****XX:HeapSizePerGCThread 参数设定的大小，G1 最多分配 1 个 GC 线程，最终线程数不会超过该限制值。
-XX:ConcGCThreads= 执行并发 GC 任务所使用的最大线程数。默认取值规则：该数值为-XX:ParallelGCThreads 并行 GC 线程数除以 4。
-XX:+G1UseAdaptiveIHOP
-XX:InitiatingHeapOccupancyPercent=45		 这两项是控制堆占用启动阈值（IHOP）的默认配置：自适应 IHOP 功能默认开启；在最初的几个回收周期内，G1 会以老年代内存占用率达到 45% 作为并发标记的启动阈值。
-XX:G1HeapRegionSize=<ergo> 堆分区的大小。默认值基于最大堆容量计算，JVM 会自动调整该值，使堆内分区总数约等于 2048 个。分区大小必须是 2 的幂次方，合法取值范围为 1MB ~ 32MB。
-XX:G1NewSizePercent=5
-XX:G1MaxNewSizePercent=60		 新生代整体堆大小，会以当前已使用 Java 堆的占比为基准，在这两个数值区间内动态浮动。
-XX:G1HeapWastePercent=5 该参数设定收集集合候选分区中允许保留的不可回收空间占比阈值。若收集集合候选分区中的可释放空闲空间占比低于此阈值，G1 便会结束空间回收阶段。
-XX:G1MixedGCCountTarget=8 指定空间回收阶段预期执行的混合 GC 总轮次。
-XX:G1MixedGCLiveThresholdPercent=85 老年代分区存活对象占比超过该阈值时，不会在当前空间回收阶段被纳入回收。

：实际参数值会由 JVM 根据运行环境自适应自动推算。

关于-XX:G1MixedGCCountTarget=8的补充释义：G1 会把空间回收阶段需要清理的老年代分区，分摊到目标设定的 8 轮混合 GC 中逐步回收。

与其他垃圾收集器对比

本节总结 G1 与其他垃圾收集器的主要差异：

  • 并行 GC 只能整体一次性对老年代做内存整理与空间回收；而 G1 把这部分工作增量拆分，分摊到多次耗时短得多的 GC 中逐步完成。该方式能大幅降低停顿时间，代价是会牺牲一定吞吐量。
  • G1 会以并发形式完成部分老年代的空间回收工作。
  • 受并发运行特性影响，G1 的运行开销通常高于上述收集器，进而对系统吞吐量产生影响。
  • ZGC 面向超大堆场景设计，目标是实现远低于 G1 的停顿时间，吞吐量损耗也会更大。

基于自身运行机制，G1 具备若干独有机制来提升垃圾回收效率：

  1. G1 可在任意 GC 阶段，回收老年代中整片完全空闲的大块内存区域。这能避免大量不必要的 GC，以极小开销释放可观内存空间。
  2. G1 支持可选并发对 Java 堆内重复字符串进行去重。

老年代空闲巨型对象回收默认永久启用；可通过参数 -XX:-G1EagerReclaimHumongousObjects 关闭。字符串去重功能默认关闭，可通过 -XX:+UseStringDeduplication 手动开启。

8 G1 垃圾收集器调优

本节介绍当 G1 垃圾收集器（G1 GC）的运行表现无法满足业务需求时，如何对其工作行为进行适配与调优。

G1 通用调优建议

通用最佳实践：优先使用 G1 默认配置；如有需要，可另行设定GC 停顿时间目标，并通过 -Xmx 指定 Java 最大堆内存。

G1 默认参数的平衡策略与其他垃圾收集器完全不同。默认配置下，G1 既不以极致吞吐量为目标，也不追求极致低延迟，而是兼顾高吞吐量，同时提供幅度小、波动平稳的 GC 停顿。但 G1 为实现堆内存增量回收、停顿时间可控所设计的机制，会给应用业务线程和空间回收效率带来一定额外开销。

若业务更看重高吞吐量，可放宽 -XX:MaxGCPauseMillis 停顿时间限制，或调大堆内存空间。若以低延迟为核心诉求，则按需调整停顿时间目标。尽量避免使用 -Xmn、-XX:NewRatio 等参数强制限定新生代大小：新生代容量是 G1 达成停顿时间目标的核心调控手段。一旦手动固定新生代尺寸，会覆盖 G1 自适应逻辑，实质上丧失停顿时间自动管控能力。

从其他垃圾收集器迁移至 G1

通常从其他收集器（尤其是 CMS 并发标记清除收集器）迁移到 G1 时，建议先移除所有垃圾回收相关自定义参数，只通过 -Xmx 设置最大堆内存，必要时搭配 -Xms 设置初始堆内存，并配置停顿时间目标即可。

许多为其他收集器定制的调优参数，对 G1 要么完全无效，要么反而会降低吞吐量、削弱 G1 达成停顿时间目标的能力。典型示例：手动硬性指定新生代大小，会彻底限制 G1 动态调节新生代容量的能力，使其无法适配停顿时间目标。

G1 性能优化

G1 在设计上无需额外配置参数，就能提供良好的综合性能。但在部分场景下，其默认启发式策略与配置无法达到最优效果。本节针对这类场景，给出问题诊断与性能调优的指导思路。本文仅说明：在应用程序代码固定的前提下，如何借助 G1 自身能力，针对特定性能指标优化垃圾回收表现。实际落地中，应用层优化往往比单纯调优虚拟机更有效。例如减少长生命周期对象的创建，从根源规避各类 GC 异常场景。

为便于问题排查诊断，G1 提供了完善的日志能力。建议先启用参数 -Xlog:gc*=debug 打印详细 GC 日志，必要时再按需精简日志输出。该日志会完整记录 GC 停顿期间及非停顿阶段的所有回收行为，包含 GC 类型、以及停顿内各子阶段的耗时细分数据。

后续小节将逐一分析常见的 G1 性能问题场景。

观测全局垃圾回收（Full GC）

全局堆垃圾回收（Full GC）通常耗时极长。日志中出现 Pause Full (Allocation Failure) 标识，代表因老年代堆占用率过高触发了 Full GC。Full GC 发生前，一般都会先出现垃圾回收转移失败的情况，日志特征为to-space exhausted（目标空间耗尽）。

触发 Full GC 的本质原因是：应用创建对象的速度过快，垃圾回收无法及时完成内存回收。多数时候是并发标记未能按时结束，导致无法正常进入空间回收阶段。大量巨型对象的分配会进一步加剧 Full GC 触发概率；受 G1 对巨型对象的分配机制影响，这类对象实际占用的内存往往会远超预期。

调优的核心目标是确保并发标记能够按时完成。实现方式有两种：降低老年代的对象分配速率，或是给并发标记预留更多执行时间。

G1 提供了多种配置方案来优化该场景：

  • 开启gc+heap=info日志，可查看 Java 堆中巨型对象占用的分区数量。日志行Humongous regions: X->Y里的 Y 即为巨型对象占用的分区总数。若该数值相对于老年代分区总数占比过高，最优做法是减少业务中巨型对象的产生；也可通过-XX:G1HeapRegionSize调大堆分区尺寸来优化。JVM 启动日志开头会打印当前生效的堆分区大小。
  • 调大Java堆内存上限，通常能为并发标记留出更充裕的执行时间。
  • 手动设置-XX:ConcGCThreads，增加并发标记线程数。
  • 让 G1 提前启动标记周期。G1 默认会根据应用历史运行行为，自适应计算堆占用启动阈值 IHOP；若应用运行特征发生改变，这套自适应预测就会失效。有两种解决方式：修改-XX:G1ReservePercent，增大 IHOP 自适应计算的预留缓冲，降低触发空间回收的堆占用目标阈值；关闭 IHOP 自适应计算，通过 -XX:-G1UseAdaptiveIHOP 配合-XX:InitiatingHeapOccupancyPercent手动指定 IHOP 阈值。

除分配失败外，其他原因触发的Full GC，一般都是应用代码或外部工具主动调用所致。如果是System.gc()触发且无法修改应用源码，可通过-XX:+ExplicitGCInvokesConcurrent将显式 GC 转为并发回收，减轻 Full GC 影响；也可配置-XX:+DisableExplicitGC，让JVM 直接忽略所有显式 GC 调用。外部监控工具仍可能强制触发 Full GC，这类情况只能关闭工具的GC请求调用才能彻底解决。

巨型对象内存碎片化

由于巨型对象必须分配在连续的堆分区中，因此即便 Java 堆总内存尚未耗尽，也可能因无法找到连续空间而触发 Full GC。针对该问题的解决方案：使用-XX:G1HeapRegionSize调大堆分区大小，减少巨型对象的生成数量或直接增大堆内存容量。极端场景下，即使堆内剩余内存总量充足，G1 也可能无法找到足够的连续空间分配巨型对象。若触发的 Full GC 仍无法回收出足够的连续空间，将直接导致 JVM 进程退出。这种情况下没有其他优化手段，只能按照前文所述减少巨型对象的分配，或者增大堆内存。

延迟调优

本节针对常见的延迟问题（即 GC 停顿时间过长的场景），提供优化 G1 回收行为的调优建议。

非常规系统负载与实时业务场景

每次垃圾回收停顿期间，开启gc+cpu=info日志后，会输出一行操作系统维度的耗时拆解信息，记录 GC 停顿阶段的时间开销分布。典型日志示例：User=0.19s Sys=0.00s Real=0.01s。

用户态耗时是虚拟机自身代码执行耗时；系统态耗时是陷入操作系统内核执行的耗时；实际耗时是本次 GC 停顿流逝的绝对时钟时长。若系统态耗时明显偏高，问题根源通常出在运行环境层面。

造成系统态耗时过高的常见典型问题：

  • JVM 向操作系统动态申请、归还内存，会引入不必要的延迟。

    规避方式：将 -Xms 初始堆与 -Xmx 最大堆设为相同值；同时开启 -XX:+AlwaysPreTouch 预触碰全部堆内存，把内存初始化开销转移到 JVM 启动阶段。

  • 在 Linux 环境下，透明大页（THP） 会自动将内存小页合并为大页，该机制容易随机阻塞进程，且阻塞不只发生在 GC 停顿期间。由于 JVM 需分配和管理海量内存，被长时间阻塞的风险远高于普通进程。可参照操作系统官方文档关闭透明大页功能。

  • 日志写入引发卡顿：后台任务会间歇性占满日志所在磁盘的 I/O 带宽，拖慢 GC 日志落盘。

    优化方案：将日志单独挂载至独立磁盘，或使用内存文件系统等存储介质，隔离 I/O 争抢。

另一种需重点排查的现象：实际耗时远大于用户态与系统态耗时之和，这通常意味着服务器整体负载过高，JVM 进程无法获得足够的 CPU 时间片调度。

引用对象处理耗时过长

引用对象处理阶段的日志会展示引用对象（Reference Objects）的处理耗时。在该阶段中，G1 会根据不同类型引用对象的规范，更新其指向的引用目标对象（referents）。默认情况下，G1 采用以下启发式策略对引用处理的子阶段执行并行化：每处理 -XX:ReferencesPerThread 个引用对象，就启动一个工作线程，最大线程数不超过 -XX:ParallelGCThreads 的设定值。

你可以通过以下方式修改该行为：

  • 将 -XX:ReferencesPerThread 设为 0：禁用上述启发式策略，默认使用所有可用的并行线程；
  • 配置 -XX:-ParallelRefProcEnabled：完全禁用引用对象的并行处理功能。
纯年轻代阶段中的年轻代回收耗时过长

常规的年轻代回收（以及所有类型的年轻代回收），其耗时大致与新生代大小成正比；更精准地说，与回收集中需要复制的存活对象数量成正比。如果回收集转移（Evacuate Collection Set）阶段耗时过长（尤其是对象复制（Object Copy）子阶段），可降低-XX:G1NewSizePercent参数值。该操作会减小新生代的最小容量，从而有效缩短 GC 停顿时间。

若应用性能（尤其是一次回收后存活的对象数量）突然发生变化，新生代的容量配置也可能引发问题，导致GC 停顿时间出现尖峰。针对这种情况，可通过降低-XX:G1MaxNewSizePercent来限制新生代的最大容量，以此控制停顿阶段需要处理的对象总量。

混合回收耗时过长

混合回收用于回收老年代空间，混合回收的回收集同时包含新生代和老年代分区。开启 gc+ergo+cset=trace 日志，可精准查看新生代分区转移、老年代分区转移分别对 GC 停顿时间的耗时贡献，重点关注日志中的预测新生代分区耗时和预测老年代分区耗时指标。

若预测新生代分区耗时过长，可参考前文「纯年轻代阶段中的年轻代回收耗时过长」的优化方案；若需降低老年代分区对停顿时间的影响，G1 提供三种调优手段：

  • 增大 -XX:G1MixedGCCountTarget：将老年代分区的回收工作分摊到更多轮 GC 中执行；
  • 调整 -XX:G1MixedGCLiveThresholdPercent：过滤掉回收耗时过长的分区，不将其加入候选回收集（通常存活对象占比极高的分区，回收耗时会显著增加）；
  • 调高 -XX:G1HeapWastePercent：提前终止老年代空间回收，减少高占用分区的回收数量。

需要注意的是，后两种优化方案会减少当前空间回收阶段的候选回收分区数量，可能导致 G1 无法回收足够的老年代空间以支撑应用持续运行；不过这些未回收的分区，可在后续的空间回收阶段中处理。

记忆集更新与扫描耗时过高

为支持 G1 对单个老年代分区做对象转移回收，JVM 需要追踪跨分区引用（即从一个分区指向另一个分区的对象引用）。所有指向某一个分区的跨分区引用集合，就称作该分区的记忆集（Remembered Set，RS）。当分区内对象数据发生迁移时，必须同步更新对应的记忆集。分区记忆集的维护工作绝大部分以并发方式执行。出于性能考量，当应用在两个对象间新建跨分区引用时，G1 并不会立即更新记忆集，而是将记忆集更新请求延迟积攒、批量处理，以此提升整体效率。

垃圾回收必须依赖完整可用的记忆集，因此 GC 的记忆集更新（Update RS）阶段会处理所有积压未完成的记忆集更新请求。记忆集扫描（Scan RS）阶段则遍历记忆集中的对象引用、迁移分区数据，并将原有对象引用修正为新的内存地址。根据应用特性不同，这两个阶段可能会占用大量 GC 停顿时间。

通过 -XX:G1HeapRegionSize 调整堆分区大小，会直接改变跨分区引用的数量以及记忆集的占用规模。记忆集维护本身是 GC 工作的重要组成部分，会直接影响可达到的最大停顿时间。增大分区尺寸通常会减少跨分区引用数量，从而降低记忆集的处理开销；但同时单个分区内的存活对象会变多，反而会增加 GC 其他阶段的耗时。

G1 会调度记忆集更新的并发任务，控制记忆集更新阶段的耗时占最大允许停顿时间的比例，由参数 -XX:G1RSetUpdatingPauseTimePercent 指定。调小该参数，G1 通常会把更多记忆集更新工作放到并发时段执行，减少停顿内开销。

应用频繁分配大对象时，可能出现记忆集更新耗时莫名飙升的现象。根源是 JVM 为减少并发记忆集更新开销，做了批量合并更新的优化；若恰好于 GC 触发前产生了一大批待处理任务，这些任务就会全部积压到 GC 停顿的记忆集更新阶段集中处理。可通过 -XX:-ReduceInitialCardMarks 关闭该优化策略，规避此类突发耗时尖峰。

记忆集扫描耗时，还取决于 G1 为控制记忆集内存占用所做的压缩粒度。记忆集在内存中存储得越紧凑，GC 读取解析其中数据的耗时就越高。G1 会根据分区记忆集的当前大小，自动执行记忆集粗化完成压缩。压缩级别越高，读取原始数据的速度就越慢。搭配 gc+remset=trace 日志级别与参数 -XX:G1SummarizeRSetStatsPeriod，可以观测是否触发了记忆集粗化。在 GC 前置汇总日志中，Did <X> coarsenings 里的数值 X 若偏高，说明粗化操作非常频繁。可大幅调大-XX:G1RSetRegionEntries 参数，以此减少记忆集粗化的发生次数。生产环境不建议开启记忆集详细日志，这类日志的数据采集本身会产生极大性能开销。

吞吐量调优

G1 默认策略会在吞吐量与延迟之间做平衡；但部分业务场景会更追求更高吞吐量。除了前文所述缩短单次 GC 停顿时间外，还可以降低 GC 停顿的发生频率。核心思路是通过 -XX:MaxGCPauseMillis 调大最大允许停顿时间，分代大小启发式机制会自动适配新生代容量，而新生代大小直接决定 GC 停顿的频繁程度。若该方式达不到预期效果（尤其在空间回收阶段），可调高 -XX:G1NewSizePercent 增大新生代最小占比，强制 G1 扩大新生代。

某些场景下，新生代最大容量参数 -XX:G1MaxNewSizePercent 会限制新生代上限，进而拖累吞吐量。可开启 gc+heap=info 查看分区汇总日志辅助诊断：若伊甸分区与幸存分区总和占整体分区比例已接近该参数设定值，说明已触达上限，此时应适当调高 -XX:G1MaxNewSizePercent。

提升吞吐量的另一种方式：减少并发任务量。其中记忆集并发更新往往会消耗大量 CPU 资源。调大 -XX:G1RSetUpdatingPauseTimePercent，可将部分并发记忆集更新工作转移到 GC 停顿阶段执行。极端场景下可彻底禁用记忆集并发优化，配置如下：

9 Z 垃圾收集器

Z 垃圾收集器（ZGC）是一款可扩展的低延迟垃圾收集器。ZGC 所有耗时繁重的工作均以并发方式执行，暂停应用线程的时间不超过数毫秒，非常适合有低延迟诉求的应用。ZGC 的停顿时间与堆内存大小无关，支持的堆内存容量范围为 8MB 至 16TB。

可通过命令行参数 -XX:+UseZGC 启用 Z 垃圾收集器。

堆内存大小设置

对 ZGC 来说，最重要的调优配置就是设置最大堆内存（-Xmx）。由于 ZGC 是一款并发垃圾收集器，设定最大堆大小时必须满足两点要求：

  1. 堆内存可容纳应用的存活对象集；
  2. 堆内预留足够富余空间，确保垃圾回收运行期间应用的内存分配能正常进行。

所需富余空间的大小，很大程度取决于应用的内存分配速率和存活对象集规模。一般而言，给 ZGC 分配的内存越大，整体表现越好。但同时也不应浪费内存资源，因此关键是在内存占用与 GC 执行频率之间找到合理平衡点。

设置并发 GC 线程数

第二项需要重点关注的调优参数是并发GC线程数（-XX:ConcGCThreads）。ZGC内置启发式算法，可自动计算并配置该线程数。该算法在常规场景下表现优异，但针对具备特殊运行特征的应用，仍需手动调整。

该参数的核心作用是限定垃圾回收可占用的 CPU 时间：

  • 线程数设置过高：GC会过度抢占CPU资源，挤压应用程序的执行时间；
  • 线程数设置过低：应用程序的对象分配（垃圾产生）速度会超过ZGC的回收速度，引发内存回收滞后问题。

向操作系统归还空闲内存

默认情况下，ZGC 会释放未使用的内存，并将其归还给操作系统。对于关注内存占用开销的应用和运行环境，该特性非常实用。可以通过 -XX:-ZUncommit 关闭此功能。同时，内存归还操作不会让堆大小收缩至最小堆（-Xms）以下。若将最小堆 -Xms 与最大堆 -Xmx 设置为相同值，该内存归还特性会被隐式禁用。

可通过 -XX:ZUncommitDelay=<秒数> 配置内存归还延迟，默认值为 300 秒。该延迟用于指定内存必须空闲多久之后，才允许被回收并归还给操作系统。

终结机制与弱引用、软引用、虚引用

部分应用会通过 终结机制（Finalization）以及弱引用、软引用、虚引用，与垃圾回收进行交互。

但官方不推荐使用终结机制，该机制会引发安全性、性能和可靠性问题。例如，依赖终结机制关闭文件描述符，会导致外部资源（文件描述符）的释放完全依赖垃圾回收的执行时机。

终结机制已在 JDK 9 中被标记为废弃（Deprecated）。

终结机制

一个类可以声明终结器：即 protected void finalize() 方法，该方法的作用是释放对象持有的底层资源。垃圾回收器会将不可达对象的终结器加入执行队列，并在回收该对象内存之前调用这个方法。

当不存在从 GC 根节点指向该对象的引用路径时，对象会变为不可达状态，进而满足垃圾回收的条件。GC 根节点包含：活跃线程中的引用、JVM 内部引用；正是这些根引用让对象保留在内存中不被回收。

从终结机制迁移

为避免使用终结机制，可采用以下替代技术：

  • try-with-Resources 语句
  • Cleaner API（清理器 API）
try-with-resources 语句

try-with-resources 语句是一种支持声明一个或多个资源的 try 语句。资源指程序使用完毕后必须执行关闭操作的对象。该语句可以确保在代码块执行完毕后自动关闭所有资源，即便执行过程中发生一个或多个异常，也能保证资源正常关闭。更多详情可参考官方文档中try-with-resources 语句The Try-with-resources Statement相关章节。

Cleaner API

如果你预计应用中资源的生命周期会超出 try-with-resources 语句的作用域，可改用 Cleaner API。该 API 允许程序为对象注册一个清理动作，当对象变为不可达状态后的某个时间点，该清理动作会自动执行。

Cleaner 能够规避终结器的诸多缺陷：

  • 安全性更高：清理器必须显式注册对象；此外，清理动作无法访问目标对象，因此对象复活问题不复存在。
  • 性能更优：可自主控制清理动作的注册时机，确保清理动作永远不会处理未初始化 / 部分初始化的对象；同时支持取消对象的清理动作。
  • 可靠性更强：可指定执行清理动作的线程。

但与终结器相同，清理动作由垃圾回收器调度执行，因此可能存在无界延迟。严禁在需要及时释放资源的场景中使用 Cleaner API。

引用对象类型

引用对象包含三种类型：软引用（SoftReference）、弱引用（WeakReference） 和虚引用（PhantomReference）。每种引用对象类型对应不同级别的可达性。以下是从强到弱排序的可达性级别，完整反映了对象的生命周期：

  • 强可达：线程无需遍历任何引用对象即可访问的对象，为强可达对象。新创建的对象，对创建它的线程而言就是强可达的。
  • 软可达：对象非强可达，但通过遍历软引用可访问到，则为软可达。
  • 弱可达：对象既非强可达、也非软可达，但通过遍历弱引用可访问到，则为弱可达。当指向弱可达对象的弱引用被清除后，该对象将满足终结机制的执行条件。
  • 虚可达：对象既非强、软、弱可达，已完成终结处理，且存在虚引用指向该对象，则为虚可达。
  • 不可达：对象不满足上述任何可达性条件时，即为不可达状态，满足内存回收条件。

每种引用对象都会封装对一个特定目标对象的引用，该目标对象被称为引用目标（referent）。引用对象提供了专门的方法，用于清除对目标对象的引用。

引用对象实例的常见用途：

  • 保留对象的访问权限，同时允许 JVM 在内存不足时回收该对象（适用于可重新生成的缓存数据）；
  • 结合 ReferenceQueue 类，监控对象的可达性状态，并在对象达到指定状态时执行自定义操作。

显式垃圾回收

应用程序与垃圾回收交互的另一种方式，是通过调用 System.gc() 方法显式触发完整垃圾回收。

该方法会在非必要场景下强制触发全局垃圾回收（Major GC）（例如仅需执行新生代小型回收 Minor GC 即可满足需求时），因此通常应当避免手动调用。我们可以通过 -XX:+DisableExplicitGC 参数禁用显式垃圾回收，以此评估其对性能的影响；该参数会让 Java 虚拟机直接忽略所有 System.gc() 调用。

软引用

软引用在服务器版虚拟机中的存活时长，会比客户端版虚拟机更长。

我们可以通过命令行参数 -XX:SoftRefLRUPolicyMSPerMB=<N> 控制软引用的清除速率。该参数的含义是：当对象不再具备强可达性后，堆内存中每 1 兆字节的空闲空间，对应软引用能够保持存活的毫秒数。该参数的默认值为每兆字节 1000 毫秒。这意味着（在对象的最后一个强引用被回收后），堆内存中每拥有 1MB 空闲空间，该对象的软引用就会额外存活 1 秒。该数值为近似值，因为软引用仅会在垃圾回收执行期间被清除，而 GC 的触发时机是不固定的。

类元数据

Java 类在 HotSpot 虚拟机内部存在对应的内存表示形式，被称为类元数据。

在早期的 HotSpot 虚拟机版本中，类元数据分配在永久代中。从 JDK 8 开始，永久代被移除，类元数据转而分配在本地内存中。默认情况下，用于存储类元数据的本地内存大小无上限；可通过 -XX:MaxMetaspaceSize 参数为其设置最大使用上限。

HotSpot 虚拟机对类元数据的内存空间进行显式管理：先向操作系统申请内存，再将内存划分为多个内存块。类加载器从所属的内存块中为类元数据分配空间（每个内存块仅绑定一个特定的类加载器）。当类加载器加载的类被卸载后，其对应的内存块会被回收复用，或归还给操作系统。类元数据使用 mmap 内存映射方式分配空间，而非 malloc 标准内存分配方式。

若同时开启 -XX:UseCompressedOops（压缩普通对象指针）和 -XX:UseCompressedClassesPointers（压缩类指针），虚拟机会使用两块逻辑独立的本地内存区域存储类元数据。-XX:UseCompressedClassPointers 会在 64 位进程中使用 32 位偏移量表示类指针，其原理与 -XX:UseCompressedOops 压缩 Java 对象引用一致。虚拟机会为这些压缩类指针单独分配一块内存区域，其大小可通过 -XX:CompressedClassSpaceSize 设置，默认值为 1GB。压缩类指针的内存空间在虚拟机初始化时通过 mmap 预先保留，并根据实际需求提交使用。-XX:MaxMetaspaceSize 的限制范围包含：已提交的压缩类空间 + 其他类元数据占用的总空间。

当对应的 Java 类被卸载时，其类元数据会被释放。Java 类的卸载由垃圾回收触发，虚拟机也会主动触发垃圾回收，以完成类卸载和类元数据释放。当类元数据的已提交内存达到特定阈值（水位线）时，会自动触发垃圾回收。垃圾回收完成后，水位线会根据元数据释放的内存空间大小调高或调低；调高水位线的目的是避免短时间内重复触发垃圾回收。水位线的初始值由命令行参数 -XX:MetaspaceSize 设定，后续会根据 -XX:MaxMetaspaceFreeRatio（最大元空间空闲比率）和 -XX:MinMetaspaceFreeRatio（最小元空间空闲比率）动态调整：

  • 若类元数据的可用已提交空间占总已提交空间的比例，大于最大元空间空闲比率，则降低水位线；
  • 若该比例小于最小元空间空闲比率，则调高水位线。

调高 -XX:MetaspaceSize 的值，可避免因类元数据问题过早触发垃圾回收。该参数的取值完全依赖应用自身的类元数据占用量，无通用的配置标准；其默认值随平台不同而变化，范围为 12MB ~ 20MB。
