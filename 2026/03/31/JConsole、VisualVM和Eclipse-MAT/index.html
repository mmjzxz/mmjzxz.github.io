JConsole、VisualVM和Eclipse-MAT

工具整体对比

核心价值

  • 排查性能瓶颈：定位CPU占用过高、方法执行耗时过长等问题
  • 检测内存泄漏：发现对象未释放、内存持续增长等隐患
  • 分析线程问题：识别线程死锁、阻塞、竞争等资源冲突
  • 保障应用稳定性：预防OOM（内存溢出）、服务宕机等严重故障

定位差异

工具 定位 特点
JConsole 轻量监控 JDK自带，开箱即用，适合快速查看基础指标
VisualVM 全能分析 功能全面，支持监控、剖析、快照分析，可扩展插件
Eclipse MAT 内存专项 专业内存分析，深度排查内存泄漏和大对象问题

工具整体对比

  • 开发主体与开源情况：JConsole和VisualVM均为JDK自带工具（VisualVM后续由独立团队迭代），开源免费；Eclipse MAT由Eclipse基金会开发，独立于JDK，开源免费，可与Eclipse集成使用。
  • 核心功能侧重：JConsole聚焦实时监控，仅提供基础的内存、线程、类加载等监控能力；VisualVM兼顾实时监控与深度分析，支持采样、剖析、快照生成与分析等功能；Eclipse MAT专注于堆内存快照分析，核心能力是内存泄漏检测、大对象定位与引用链分析。

JConsole

注：以Java17版本为例。

工具基础信息

简介

JConsole是JDK自带的轻量级JVM监控工具，自JDK 5起内置，无需额外下载安装，开箱即用。其核心特点是轻量、简洁、实时性强，能够快速监控JVM的核心运行指标，适合快速排查基础的性能问题。

开发主体与版本迭代

由Oracle（原Sun公司）开发，跟随JDK版本同步迭代，核心功能无重大变更，仅在界面交互、监控精度上有小幅优化。例如，JDK 8与JDK 11中的JConsole功能基本一致，可适配对应版本的JVM进程。

核心定位

实时监控JVM运行状态，快速定位基础性能问题（如内存异常增长、线程死锁、CPU使用率过高等），为开发调试和简单性能监控提供支撑，不具备深度分析能力。

运行环境要求

需与被监控的JVM进程使用相同或兼容的JDK版本（建议版本一致，避免连接失败）；支持Windows、Linux、macOS等主流操作系统，无需额外依赖环境。

安装与启动

安装方式

JConsole无需单独安装，JDK安装完成后自动附带，具体路径如下：

  • Windows系统：JDK安装目录下的bin文件夹，如”D:\Program Files\Java\jdk1.8.0_301\bin\jconsole.exe”，双击即可启动。
  • Linux/macOS系统：JDK安装目录下的bin文件夹，执行命令”./jconsole”即可启动。

启动步骤

  • 本地启动：启动JConsole后，会自动扫描本地正在运行的Java进程，在弹出的”JConsole：新建连接”窗口中，选择需要监控的进程（如”java -jar xxx.jar”启动的应用进程）点击”连接”即可进入监控界面。若进程未被识别，可检查JDK版本是否匹配，或进程是否正常运行。
  • 远程连接：若需监控远程服务器上的Java进程，需先配置远程JVM的JMX参数，再通过JConsole连接。具体配置步骤如下：
    1. 在远程服务器的Java应用启动命令中，添加JMX相关参数：
      -Dcom.sun.management.jmxremote.port=1099（JMX端口，可自定义，需确保端口未被占用）
      -Dcom.sun.management.jmxremote.ssl=false（关闭SSL加密，简化配置）
      -Dcom.sun.management.jmxremote.authenticate=false（关闭身份验证，生产环境可开启并配置账号密码）
      -Djava.rmi.server.hostname=远程服务器IP（指定远程服务器IP，避免连接时出现地址解析问题）
    2. 重启Java应用，确保JMX参数生效，同时开放服务器的1099端口（防火墙放行）。
    3. 本地启动JConsole，在”JConsole：新建连接”窗口中选择”远程进程”，输入远程服务器IP:端口（如”192.168.1.100:1099”），点击”连接”即可完成远程监控。

核心功能

JConsole的界面主要包含”概览””内存””线程””类””VM摘要””MBean”6个核心页面，以下详细说明：

概览页

概览页是JConsole的默认首页，以曲线图形式实时展示JVM的4个核心指标，直观反映JVM运行状态。

  • 核心指标监控：
    • 堆内存使用：展示堆内存的实时使用量，曲线波动反映内存分配与GC情况，若曲线持续上升且无明显下降，可能存在内存泄漏。
    • 线程数：展示当前JVM的线程总数，包括活跃线程数、守护线程数，曲线突变（如突然激增）可能是线程创建过多或线程泄漏。
    • 类加载数：展示已加载的类数量与卸载的类数量，若已加载类数量持续增长且无卸载，可能存在类加载器泄漏。
    • CPU使用率：展示JVM进程占用的CPU百分比，若使用率持续过高（如超过80%），可能存在CPU密集型方法或线程阻塞问题。
  • 图表解读：各指标曲线均以时间为横轴，数值为纵轴。正常情况下，各曲线应呈现周期性波动（如堆内存随GC周期性下降）；若曲线出现异常波动（如突然飙升、持续上升），需进一步排查对应页面的详细信息。

内存页

JConsole 内存页用于实时监控 JVM 内存使用情况，包含堆内存、非堆内存及多个内存池的详细数据，可通过图表直观查看变化趋势并手动触发垃圾回收。

内存泄漏初步判断：通过持续监控内存曲线，若堆内存使用率持续上升，多次手动GC后仍无法明显下降，且应用无明显业务峰值，可初步判断存在内存泄漏，需进一步使用VisualVM或MAT进行深度分析。

内存分区监控

页面按堆内存、非堆内存两大维度展示内存使用趋势，可通过下拉菜单切换查看不同内存池的使用数据。

手动执行 GC

页面右侧设有「执行 GC」按钮，点击后可手动触发一次 Full GC，通过观察 GC 前后的内存数值与曲线变化，判断内存回收效果。若手动 GC 后内存大幅下降且后续增长平缓，说明内存分配合理；若 GC 后内存降幅极小，且持续走高，则存在异常内存占用的可能。

线程页（Threads）

线程页用于监控JVM的线程状态，检测线程死锁，查看线程堆栈信息，是排查线程相关问题（如死锁、线程阻塞、线程泄漏）的核心页面。

线程数监控

页面顶部以图标形式显示当前线程总数、活跃线程数，实时反映线程运行状态。若线程总数持续增长，可能存在线程泄漏（如线程创建后未正常关闭）。

线程详情和堆栈

页面下方显示所有线程的列表，可通过线程名称筛选目标线程。选中某个线程，可查看该线程的名称、状态和调用堆栈信息，包括当前执行的方法、类名、行号，可用于定位线程阻塞、耗时过长的具体原因。

线程死锁检测

页面右侧有”检测死锁”按钮，点击后可自动检测当前JVM是否存在死锁。

类页（Classes）

类页用于监控JVM的类加载与卸载情况，帮助排查类加载相关问题（如类加载过多、类加载器泄漏）。

  • 加载总数、已加载类数量监控：页面以曲线图形式展示加载总数、已加载类数量的变化趋势，同时显示当前已加载类总数、已卸载类总数。
  • 类加载/卸载趋势分析：正常情况下，应用启动初期，已加载类数量会快速增长，启动完成后趋于稳定，偶尔有类卸载；若已加载类数量持续增长，且无卸载，可能存在类加载器泄漏（如自定义类加载器未被回收，导致加载的类无法卸载），需进一步排查类加载逻辑。

VM 概要（VM Summary）

VM摘要页用于查看JVM与系统的基础信息，为问题排查提供环境参考，无需实时监控，按需查看即可。

  • JVM基础信息：包括JVM版本、厂商、启动参数（如堆内存大小、GC算法等）、类路径、模块路径等，可用于确认JVM配置是否合理（如堆内存大小是否适配应用需求）。
  • 系统信息：包括操作系统名称、版本、CPU核心数、系统总内存、空闲内存等，可用于判断系统环境是否存在资源瓶颈（如CPU核心数不足、系统内存紧张）。
  • 类加载器信息：展示当前JVM的类加载器（如Bootstrap ClassLoader、Extension ClassLoader、Application ClassLoader）及其加载的类数量，可用于排查类加载器相关问题。

MBean页（MBeans）

核心定义

JMX（Java Management Extensions） 的核心组件，用于封装和暴露 JVM 及应用程序的可管理资源，提供标准化的属性查看和方法调用接口，实现对 JVM 的精细化管理和监控。

核心作用
  • 资源封装：将 JVM 资源（内存、线程、GC、类加载等）封装为可管理的 Bean 对象
  • 属性暴露：提供属性的读取（get）和写入（set）接口，实时监控资源状态
  • 操作调用：提供可执行的方法（operation），如触发 GC、生成线程快照等
  • 通知机制：支持属性变化时的事件通知，实现主动监控告警

JConsole 操作说明
  • 属性查看
    • 选中 MBean → 属性（Attributes） 标签页
    • 查看属性当前值（如 HeapMemoryUsage.used）
    • 可写属性可直接修改（如 Verbose 开启 GC 日志）
  • 方法调用
    • 选中 MBean → 操作（Operations） 标签页
    • 点击 “调用” 按钮执行方法
    • 部分方法需要参数（如 findDeadlockedThreads() 无需参数）
  • 通知订阅
    • 选中 MBean → 通知（Notifications） 标签页
    • 订阅属性变化事件（如内存阈值告警）
重要限制与注意事项
  • 不可动态修改的参数
    • 堆内存大小（-Xmx、-Xms）：无法通过 MBean 修改，需重启 JVM
    • 代码缓存大小：无法动态调整
    • 可修改的参数：部分日志级别、GC 详细输出开关等
  • 安全配置（远程访问时）：
    • 启用 SSL/TLS 加密 连接
    • 配置 用户名/密码认证（-Dcom.sun.management.jmxremote.password.file）
    • 限制 访问 IP 地址（-Dcom.sun.management.jmxremote.host）
    • 生产环境不建议开放远程 JMX，优先使用本地连接或 JMC
  • 性能影响
    • 频繁调用 MBean 方法可能影响应用性能
    • 通知机制会消耗额外资源，按需订阅

适用场景

JConsole的核心优势是轻量、实时、操作简单，其适用场景主要包括：

  • 本地开发调试：开发过程中，快速监控应用的内存、线程状态，验证代码逻辑（如避免线程死锁、内存泄漏）。

  • 简单性能监控：测试环境或生产环境的基础监控，实时查看JVM核心指标，快速发现异常（如CPU过高、内存激增）。

  • 快速排查基础问题：无需复杂操作，即可初步判断内存泄漏、线程死锁、类加载异常等基础问题，为后续深度分析提供方向。

VisualVM

注：以2.2.1版本为例。

工具基础信息

简介

VisualVM是一款功能全面的JVM监控与分析工具，自JDK 1.6 Update 7起内置（JDK 9及以上需独立下载），集成了JConsole、jstat、jmap、jstack等多种JDK命令行工具的功能，支持监控、采样、剖析、快照分析等多种能力，是一款”全能型”JVM分析工具。

开发主体与版本迭代

最初由Oracle（原Sun公司）开发，随JDK同步迭代；JDK 9发布后，VisualVM从JDK中分离，由VisualVM独立开发团队维护，后续版本不断优化插件生态和分析功能，目前最新版本可适配JDK 8至JDK 17等主流版本。

核心定位

全能型JVM分析工具，兼顾实时监控与深度分析，支持本地/远程进程监控、CPU/内存采样与剖析、堆/线程快照生成与分析，同时支持插件扩展，可满足开发调试、测试优化、生产环境轻量级排查等多场景需求。

运行环境要求

支持Windows、Linux、macOS等主流操作系统；JDK 8及以下版本可直接使用内置VisualVM，JDK 9及以上版本需独立下载安装，且需与被监控JVM版本兼容；部分高级功能需安装对应插件，需确保网络通畅（在线安装插件）。

安装与启动（含插件配置）

安装方式

  • JDK内置安装（JDK 8及以下）：与JConsole类似，JDK安装完成后，在bin文件夹中可找到”jvisualvm.exe”（Windows）或”jvisualvm”（Linux/macOS），双击或执行命令即可启动，无需额外配置。
  • 独立版本安装（JDK 9及以上）：由于JDK 9及以上版本移除了内置的VisualVM，需从官方网站（https://visualvm.github.io/）下载独立版本，解压后即可使用，无需安装，解压路径建议避免中文和空格。

启动步骤

本地启动

启动VisualVM后，会自动扫描本地正在运行的Java进程，在左侧”应用程序”列表中显示，双击目标进程即可进入监控与分析界面。若进程未被识别，可检查JDK版本是否兼容，或进程是否正常运行。

远程连接

与JConsole类似，需先配置远程JVM的JMX参数或JStatd参数，再通过VisualVM连接，支持两种连接方式：

JMX连接

配置方式与JConsole一致，添加JMX参数后，在VisualVM左侧”Applications”列表中右键”Remote”，选择”Add Remote Host”，输入远程服务器IP，再右键该主机，选择”Add JMX Connection”，输入端口（如1099），点击”确定”即可连接。

JStatd连接

  • 启动JStatd服务

    适用于无法配置JMX参数的场景（如生产环境限制），需在远程服务器启动JStatd服务，具体步骤如下：

    1. 新建jstatd.all.policy文件，保存到JDK的bin目录

    2. 启动 JStatd 服务

      • 以管理员身份打开 CMD 命令行（避免权限不足）；

      • 切换到 JDK 的 bin 目录（和策略文件同目录）：

      • 执行启动命令（指定策略文件和端口，端口自定义，比如 1098）：

        • -J-Djava.security.policy：指定安全策略文件路径（如果文件不在当前目录，需写绝对路径，比如C:\jdk\jstatd.all.policy）；
        • -p 1098：指定 JStatd 监听端口（默认就是 1098，可省略，自定义端口需记住）；

    3. 启动成功的标志：CMD 窗口没有报错，且不会退出（JStatd 是后台服务，窗口保持打开即可）。

  • 建立JStatd连接

    在VisualVM中添加远程主机，右键主机选择”Add jstatd connection”，输入端口，即可连接。

插件管理（核心功能扩展）

VisualVM支持插件扩展，通过安装不同的插件，可实现功能升级。

插件安装方法
在线安装

启动VisualVM，点击顶部菜单栏”工具”→”插件”，切换到”可用插件”标签页，勾选需要安装的插件（如Visual GC），点击”安装”，按照提示完成安装，重启VisualVM即可生效。

手动安装

若在线安装失败（如网络问题、插件中心地址失效），可从VisualVM官方网站下载对应插件的.nbm文件，在插件窗口切换到”已下载”标签页，点击”添加插件”，选择下载的.nbm文件，完成安装并重启。需注意插件版本与VisualVM版本匹配，避免安装失败。

插件介绍

Visual GC

最常用的插件，用于GC过程可视化，可直观展示各内存区域（Eden、Survivor、Old Gen）的GC前后变化、GC次数、GC耗时，便于优化GC参数。

Profiler

剖析器插件，默认已集成，支持CPU、内存、线程剖析，可精准统计方法执行时间、调用次数，跟踪对象创建与销毁。

Jolokia

基于 HTTP 的 JMX 代理插件，让 VisualVM 可通过 Jolokia 协议远程连接 JVM，无需直接 JMX 连接，适合跨网络、容器化环境的 JVM 监控，支持读取 MBean、执行管理操作，拓展了 VisualVM 的远程监控能力。

GraalJS

为 VisualVM 提供 Graal.js 脚本引擎支持，允许使用 JavaScript（基于 GraalVM）编写自定义监控脚本、扩展功能，比如定制面板、数据处理逻辑，满足灵活的监控定制需求。

VisualVM-Extensions

基础扩展插件，是众多其他插件的依赖基础，提供通用扩展框架、UI 组件和数据采集接口，增强 VisualVM 的可扩展性与生态兼容性。

BTrace Workbench

动态追踪工具，无需重启应用即可注入追踪代码，实时监控方法调用、参数、返回值与异常，是生产环境排查问题的利器，支持在 VisualVM 中可视化追踪结果。

Startup Profiler

启动剖析插件，专门针对 Java 应用启动阶段做性能剖析，统计类加载、初始化、方法执行耗时，帮助定位冷启动慢的瓶颈，优化应用启动速度。

VisualVM-Security

安全监控插件，可视化展示 JVM 安全管理器配置、权限策略、SSL/TLS 连接状态，监控安全相关 JVM 参数与运行时安全事件，辅助排查安全问题。

VisualVM-JConsole

集成 JConsole 功能，提供与 JConsole 一致的 MBean 查看、内存 / 线程监控界面，兼容 JConsole 操作习惯。

Threads Inspector

线程监控增强插件，在默认线程视图基础上，提供更细粒度的线程状态分析（如锁竞争、等待原因、栈深度），帮助快速定位死锁、线程阻塞等并发问题。

VisualVM-JFR Streaming

JFR（Java Flight Recorder）流式分析插件，支持实时接收并解析 JVM 生成的 JFR 事件流，无需等待完整 dump 文件，即可实时监控 CPU、内存、IO 等事件，适合持续性能追踪。

VisualVM-BufferMonitor

NIO 缓冲区监控插件，专门监控 Direct Buffer/Heap Buffer 的分配、大小、泄漏情况，解决 NIO 相关的内存溢出或泄漏问题。

VisualVM-TDA-Module

线程转储分析插件（TDA），可离线分析 thread dump 文件，可视化展示线程状态、锁持有关系、死锁检测，是定位并发问题的重要工具。

VisualVM-Coherence

Oracle Coherence 缓存专用监控插件，监控 Coherence 集群节点、数据分区、缓存项存取性能与集群状态，辅助排查分布式缓存相关问题。

VisualVM-MBeans

提供更直观的 MBean 浏览器界面，支持查看属性、调用方法、订阅通知，是 JVM 及应用管理 Bean 监控的核心工具。

Tracer-Monitor Probes

Tracer 框架下的系统级监控探针，采集 OS 层面指标（CPU 负载、内存、磁盘 / 网络 IO），将系统资源瓶颈与 JVM 指标关联分析。

Tracer-Collections Probes

Tracer 框架下的集合监控探针，针对 Java 集合框架（List/Set/Map），监控集合创建、扩容、元素操作，发现集合使用不当导致的内存泄漏或性能问题。

Tracer-JavaFX Probes

Tracer 框架下的 JavaFX 专用探针，监控 JavaFX 应用渲染性能、UI 事件处理、FPS、布局耗时，优化桌面应用流畅度。

Tracer-IO Probes

Tracer 框架下的 IO 监控探针，采集文件 / 网络 IO 读写吞吐量、延迟、调用频率，定位 IO 密集型应用的性能瓶颈。

Tracer-Swing Probes

Tracer 框架下的 Swing 专用探针，监控 Swing UI 事件派发、EDT 线程阻塞、组件渲染，解决界面卡顿、无响应问题。

Tracer-Jvmstat Probes

Tracer 框架下的 jvmstat 探针，基于 jvmstat 协议轻量采集 JVM 指标（类加载、GC 计数、线程数），适合低开销持续监控。

Tracer-JVM Probes

Tracer 框架下的核心 JVM 探针，采集 GC 各代内存、方法区、编译线程等核心指标，与 Visual GC 互补，提供全面的 JVM 运行时数据。

OQL Syntax Support

OQL（对象查询语言）语法增强插件，为堆快照分析提供语法高亮、自动补全、校验功能，方便编写 OQL 查询，高效分析堆中对象分布与引用关系。

核心功能

VisualVM 是 JVM 性能监控与故障排查的可视化工具，界面整体分为左侧 Applications 应用列表和右侧核心功能标签页两大区域。右侧功能区默认包含Overview、Monitor、Threads、Sampler、Profiler五大核心标签页，同时支持插件扩展标签页（如 Visual GC），各功能详细说明如下：

Applications

Applications 面板是 VisualVM 的进程管理总入口，负责目标 JVM 进程的发现、接入与快照资源管理。

核心功能如下：

  1. 本地进程自动发现

    Local节点会自动扫描并展示本机运行的所有 Java 进程，显示进程名称与唯一 PID，截图中可见本地运行的 VisualVM 自身进程、IntelliJ IDEA（pid 34168）进程，双击进程即可打开对应的监控面板，是所有监控分析的入口。

  2. 远程进程监控支持

    Remote节点支持配置远程主机的 JVM 进程，实现跨机器的 JVM 监控与分析，满足服务器端应用的排查需求。

  3. 离线快照管理

    VM Coredumps、JFR Snapshots、Snapshots三个节点，分别用于管理进程崩溃核心转储文件、JFR 飞行记录文件、性能分析快照文件，支持离线导入与分析，无需保持进程在线即可完成故障复盘。

Overview

Overview 为目标 JVM 进程的基础信息总览面板，汇总进程与 JVM 运行环境的核心配置信息.

核心功能如下：

  1. 进程基础元信息展示

    顶部展示进程 PID、运行主机、主类、启动参数等核心标识信息。

  2. JVM 运行环境信息

    展示 JVM 类型与版本、Java 版本、Java Home 路径、JVM 启动标志等环境信息。

  3. JVM 启动参数与配置

    分类展示完整的 JVM 启动参数，包括堆内存配置、GC 算法配置、调试参数、系统属性等；同时展示关键运行时配置状态，如是否开启内存溢出自动堆转储、是否启用 JMX 监控、是否开启类共享等。

  4. 系统属性与运行数据

    列出 JVM 系统属性（如文件编码、操作系统类型、用户目录）、已保存的诊断数据统计。

Monitor

Monitor 是实时运行状态监控仪表盘，以动态图表形式持续采集并展示 JVM 核心运行指标。

核心功能如下：

  1. CPU 使用率与 GC 监控

    实时绘制 CPU 总使用率与垃圾回收（GC）占用 CPU 比例的趋势折线图，可直观观察 CPU 负载波动、GC 触发频率与耗时。通过图表可快速定位 CPU 持续打满、频繁 Full GC 等异常场景，判断性能瓶颈是否由 GC 导致。

  2. 内存实时监控

    分为堆内存（Heap）与元空间（Metaspace）两个子模块，实时展示内存最大值、已使用值、空闲值的变化趋势。堆内存监控可观察对象创建速度、内存增长趋势，初步判断内存泄漏；元空间监控用于排查类加载过多、类加载器泄漏导致的元空间溢出问题。

  3. 类加载统计

    展示当前已加载类数量、已卸载类数量、类加载总数的实时变化曲线。用于诊断动态代理、反射、自定义类加载器导致的类加载泄漏，或类频繁加载卸载引发的性能损耗。

  4. 线程数量监控

    实时展示活跃线程数、守护线程数、线程峰值、总启动线程数，通过线程数趋势图可发现线程无限创建、线程泄漏、线程池耗尽等问题。

  5. 手动运维操作

    提供Perform GC手动触发 Full GC、Heap Dump一键生成堆转储文件的功能，可在发现内存异常时主动采集数据，为后续分析提供依据。

Threads

Threads 面板专注于JVM 线程全生命周期诊断，用于分析线程状态、线程阻塞、锁竞争、死锁、线程死循环等问题，是多线程并发问题排查的核心工具。

核心功能如下：

  1. 线程全局统计

    顶部展示当前存活线程总数、守护线程数量，提供线程可视化开关与线程快照生成按钮，一键导出完整线程堆栈（Thread Dump），用于离线分析线程调用栈与锁信息。

  2. 线程状态时间线可视化

    以时间为横轴、线程为纵轴，用不同颜色标记线程全状态：运行（Running）、休眠（Sleeping）、等待（Wait）、挂起（Park）、锁阻塞（Monitor）。可直观查看每个线程的状态切换过程，快速定位长期占用 CPU 的死循环线程、持续阻塞的锁竞争线程。

  3. 线程运行指标统计

    每个线程右侧展示 Running 运行时长、Total 总时长及占比，可快速排序找到 CPU 占用最高的线程，定位线程死循环、IO 阻塞、锁竞争等问题的根因。

  4. 线程筛选与缩放

    支持筛选活跃线程、已终止线程，可对时间线进行放大、缩小、拖拽，精准定位特定时间段的线程状态异常。

Sampler

Sampler 为采样式性能分析器，采用定时采样的方式采集 JVM 运行数据，对应用性能侵入性极低、开销小，适合生产环境快速定位性能热点，分为 CPU 采样与内存采样两大核心能力。

核心功能如下：

  1. CPU 采样

    以固定频率采集线程与方法的 CPU 占用数据，统计每个线程、每个方法的 CPU 执行时间、占比、调用次数。无需修改代码即可快速定位 CPU 热点方法，如死循环、复杂计算、频繁递归等性能瓶颈；支持配置采样频率、过滤 JDK 内置类（java.、javax. 等），减少无关数据干扰。

  2. 内存采样

    实时采集堆内存中对象的分配数据，生成堆直方图（Heap Histogram），展示各对象类型的存活数量、占用内存大小、占总堆内存比例，快速定位大对象、高频创建对象、内存占用 Top N 类型；同时支持按线程维度统计内存分配量，定位频繁创建对象的异常线程。

Profiler

Profiler 是全量埋点式深度剖析器，通过字节码增强技术对所有方法调用进行全量埋点统计，分析精度远高于采样模式，可获取完整的方法调用链路、执行耗时、分配详情，支持 CPU、Memory、JDBC、Locks 四大维度的全量分析，可分别完成 CPU 热点方法、内存分配全链路、数据库访问性能、锁竞争情况的深度统计与分析。

核心功能如下：

  1. CPU 剖析

    全量统计所有方法的调用次数、自耗时（方法自身执行时间）、总耗时（包含子方法执行时间），生成完整的方法调用树与调用链路图。精准定位执行耗时过长、调用次数过多、嵌套过深的方法，明确性能瓶颈的具体代码位置；支持自定义剖析包范围，仅监控业务代码。

    | 指标 | 核心含义 | 单位 | 本质 |
    | —————————— | —————————————————————————————— | —— | ——————————————————- |
    | Invocations | 方法被调用的总次数 | 次 | 调用频次（“多久执行一次”） |
    | Total Time | 所有调用的「墙钟时间」总和（从调用开始到结束的实际流逝时间） | ms | 总耗时（用户感知的卡顿时间） |
    | Total Time (CPU) | 所有调用的「CPU 执行时间」总和（方法真正在 CPU 上运算的时间） | ms | 总 CPU 开销（程序真正 “干活” 的时间） |

  2. 内存分配剖析

    追踪每个方法的对象分配行为，统计方法级别的对象创建数量、内存分配大小，关联对象创建与方法调用的关系。

  3. JDBC 剖析

    监控应用内所有 JDBC 数据库调用，统计 SQL 执行次数、执行耗时，定位慢 SQL、频繁重复 SQL、数据库连接泄漏等数据层性能问题。

  4. 锁与并发剖析

    监控线程锁竞争、等待、阻塞行为，统计锁等待时间、竞争次数，展示锁持有线程与等待线程的关系，定位并发场景下的锁瓶颈、线程饥饿问题。

    | 维度 | Threads 视图 | Monitors 视图 |
    | —————— | ———————————————————————— | :—————————————————————————————- |
    | 核心视角 | 以线程为中心，展示每个线程的锁持有与等待情况 | 以 锁对象（监视器） 为中心，展示每个锁的持有者与等待线程 |
    | 数据组织 | 线程 → 持有的锁 → 等待的锁 | 锁对象 → 持有线程 → 等待线程 |
    | 分析起点 | 从线程行为入手，适合排查特定线程的阻塞原因 | 从锁竞争入手，适合定位高竞争的 “热点锁” |
    | 用途 | 线程阻塞诊断、死锁线程关联分析 | 锁竞争优化、热点锁识别、锁粒度评估 |

采样（Sampling）与插桩（Instrumentation）

核心工作机制对比

特性 Sampler（采样器） Profiler（剖析器）
数据收集方式 定时（默认 10ms）获取所有线程的调用栈快照，基于统计推断方法执行时间 在类加载时修改字节码，在方法入口 / 出口插入计时逻辑，记录每次调用的精确信息
技术本质 非侵入式采样（基于 JVM 的 Thread Dump 机制） 侵入式插桩（基于 Java Instrumentation API）
是否 “全量埋点” 无埋点，仅定期快照 可配置的全量 / 部分埋点（默认过滤 JDK 类，可自定义包含 / 排除规则）
精度 统计近似值（快速执行的方法可能被遗漏） 精确值（记录每一次方法调用、执行时间、调用栈）
性能开销 极低（通常 < 5%），适合生产环境 较高（10%-50% 甚至更高），适合开发 / 测试环境

详细原理

Sampler（采样器）：轻量级的统计分析
  • 工作流程
    1. 以固定时间间隔（默认 10ms）触发线程中断
    2. 捕获所有活跃线程的当前调用栈
    3. 统计每个方法在采样点出现的频率，推算 CPU 占用时间
  • 内存采样：类似 CPU 采样，统计对象创建的频率和数量，推断内存分配热点
  • 优点：几乎不影响应用运行，可长时间开启，适合生产环境快速定位问题
  • 缺点：无法获取精确的方法调用次数和执行时间，极短方法可能被完全忽略
Profiler（剖析器）：深度精确的插桩分析
  • 工作流程
    1. 在目标类加载前，通过 Instrumentation API 修改字节码
    2. 在方法入口插入计时开始代码和调用栈记录
    3. 在方法出口插入计时结束代码，计算执行时间并记录结果
  • 配置选项：可精确控制插桩范围（包含 / 排除特定包、类、方法），避免对无关代码造成性能影响
  • 优点：提供完整的方法调用链、精确的执行时间和调用次数，支持调用图分析
  • 缺点：高开销可能改变应用行为（如触发 JIT 编译策略变化），不适合生产环境长时间运行

适用场景

VisualVM功能全面，兼顾轻量监控与深度分析，适用场景覆盖开发、测试、生产全流程，核心场景如下：

  • 开发调试阶段：实时监控应用内存、线程状态，通过采样器快速定位代码中的性能问题（如耗时方法、内存泄漏隐患），借助剖析器深度分析方法执行逻辑，优化代码质量。

  • 测试环境性能优化：通过CPU、内存剖析，精准定位性能瓶颈（如GC频繁、线程阻塞），优化GC参数、代码逻辑和线程管理策略，提升应用吞吐量和响应速度。

  • 生产环境轻量级排查：使用采样器、线程dump、堆dump功能，在不显著影响应用性能的前提下，排查线上应用的偶发问题（如间歇性卡顿、线程死锁、内存异常增长），避免剖析器对生产环境的性能影响。

  • 版本迭代后的性能验证：对比迭代前后的监控指标（如GC次数、CPU使用率、内存占用），验证优化效果，确保新版本性能不退化。

4. Eclipse MAT

工具基础信息

简介

Eclipse MAT（Memory Analyzer Tool）是一款专注于Java堆内存分析的专业工具，由Eclipse基金会开发，独立于JDK，开源免费，可与Eclipse IDE集成，也可作为独立工具使用。其核心功能是分析堆内存快照（.hprof格式），精准定位内存泄漏、大对象、内存碎片等问题，是Java内存分析领域的“利器”。

开发主体与版本迭代

由Eclipse基金会主导开发，持续迭代更新，适配最新的JDK版本和堆内存快照格式，目前最新版本支持JDK 8至JDK 24，不断优化内存分析效率和功能完整性，修复各类解析bug。

核心定位

专注于堆内存专项分析，不提供实时监控功能，核心能力包括内存泄漏检测、大对象定位、引用链分析、支配树分析等，适合深度排查内存相关问题，尤其适用于生产环境内存泄漏、OOM（Out Of Memory）问题的根源定位。

运行环境要求

支持Windows、Linux、macOS等主流操作系统；需安装JDK 8及以上版本（建议与生成堆快照的JDK版本一致）；可独立运行，也可集成到Eclipse IDE中使用，集成后可直接在IDE中分析堆快照，提升开发效率。

安装与启动

安装方式

  • 独立版本安装：从Eclipse MAT官方网站（https://www.eclipse.org/mat/）下载对应操作系统的安装包，解压后即可使用，无需安装，解压路径建议避免中文和空格，启动文件为“MemoryAnalyzer.exe”（Windows）或“mat”（Linux/macOS）。

  • Eclipse IDE集成安装：打开Eclipse IDE，点击顶部菜单栏“Help”→“Eclipse Marketplace”，搜索“Memory Analyzer”，找到对应插件后点击“Install”，按照提示完成安装，重启Eclipse即可在IDE中使用MAT功能。

启动步骤

  • 独立版本启动

    双击解压后的启动文件，启动MAT后，会弹出“Memory Analyzer”窗口，点击“File”→“Open Heap Dump”，选择需要分析的堆快照文件（.hprof格式），即可开始分析。若堆快照文件过大，启动时可能会卡顿，需调整MAT的内存分配。

  • Eclipse集成版本启动

    重启Eclipse后，点击顶部菜单栏“Window”→“Show View”→“Other”，搜索“Memory Analyzer”，打开MAT视图，然后点击“File”→“Open Heap Dump”，选择堆快照文件，即可在Eclipse中进行分析。

内存配置优化

MAT分析大型堆快照（如超过1GB）时，需要较多的内存支持，默认内存配置可能导致卡顿、崩溃，需手动优化内存配置：

  • 独立版本配置

    找到MAT安装目录下的“MemoryAnalyzer.ini”文件，修改以下参数（根据自身电脑配置调整）：

    -Xms1024m：初始内存分配，建议设置为1GB以上。

    -Xmx4096m：最大内存分配，建议设置为4GB及以上（若电脑内存充足，可设置为8GB），确保能够加载大型堆快照文件。

  • Eclipse集成版本配置：打开Eclipse安装目录下的“eclipse.ini”文件，修改上述相同参数，重启Eclipse后生效，确保集成的MAT插件有足够的内存进行分析。

支配树视图（Dominator Tree）

支配树视图用于展示对象之间的支配关系，某对象A支配对象B，意味着对象B的回收依赖于对象A的回收（只有对象A被回收，对象B才能被回收），通过支配树可快速定位内存泄漏的核心对象（支配大量内存的对象）。

支配树

如果所有从 GC Roots 到达对象 B 的引用路径，都必须先经过对象 A，那么称 A 支配 B。一旦 A 被释放（回收），所有被 A 支配的对象 B、C、D… 都会失去引用，一并被 GC 回收。

支配树的根节点是GC Roots，子节点是被GC Roots直接或间接支配的对象，支配树中每个节点的深堆大小，代表该对象支配的所有对象占用的总内存大小，节点越靠上，支配的内存越多。

Retained Heap 对象支配的总内存大小（自身 + 所有被支配对象）
Percentage 该对象支配内存占总堆内存的比例

  • 支配树筛选：支持按类名、深堆大小筛选，可快速定位目标支配对象；支持展开支配树，查看该对象支配的所有子对象，明确内存占用的具体分布。

  • 若某对象的深堆大小占堆内存总量的比例较高，且该对象的生命周期过长（如静态对象、单例对象），同时无实际业务需求持有大量子对象，可判断该对象是内存泄漏的核心，需进一步查看其引用链，释放不必要的引用。

  2. 展开支配子节点

    点击对象前的展开箭头，查看其直接支配的子对象，分析内存占用的具体构成。

    展开 ModelEntity 可看到支配了 ObservableMapWrapper、SimpleObjectProperty 等，进一步确认内存泄漏的范围。

GC Roots引用链视图（Path to GC Roots）

GC Roots是JVM中不会被GC回收的对象（如静态变量、线程对象、JNI引用等），对象若能通过引用链到达GC Roots，则无法被回收。该视图用于查看目标对象到GC Roots的引用链，是定位内存泄漏根源的关键功能。

  • 引用链生成

    选中目标对象（如直方图、支配树中的对象），右键选择“Path to GC Roots”→“exclude weak references”（排除弱引用，弱引用不会导致内存泄漏），即可生成该对象到GC Roots的引用链，清晰展示对象被哪些对象持有，最终如何关联到GC Roots。

  • 引用类型解读

    引用链中会标注引用类型（如强引用、软引用、弱引用、虚引用），只有强引用会导致对象无法被回收，若目标对象通过强引用关联到GC Roots，且无需长期持有，说明存在内存泄漏。

  • 核心作用

    精准定位对象无法被回收的原因，例如：某业务对象被静态集合持有，静态集合是GC Roots，导致业务对象无法被回收，通过引用链可直接定位到静态集合的代码位置，修复引用释放逻辑。

其他核心功能

内存泄漏报告（Leak Suspects Report）

MAT会自动分析堆快照，生成泄漏可疑报告，包含可疑对象的详细信息、引用链、内存占用情况，点击报告中的可疑点，可直接进入对应分析视图，

线程分析（Thread Overview）

展示堆快照中所有线程的信息，包括线程名称、ID、状态、持有锁信息，以及线程引用的对象，可结合线程信息排查线程相关的内存泄漏（如线程持有大量业务对象未释放）。

对比分析（Compare Heap Dumps）

导入多个堆快照文件，进行对比分析，查看对象数量、内存占用、支配树的变化，快速定位内存泄漏的源头（如某一次代码迭代后出现的内存异常增长）。

合并 GC 根最短路径（Merge Shortest Paths to GC Roots）

在支配树 / 直方图中，按住 Ctrl 键选中多个可疑对象（如批量 Lambda 监听器、多个 ModelEntity 实例）。

右键 → Merge Shortest Paths to GC Roots → 选择 exclude all phantom/weak/soft etc. references（必须排除弱 / 软 / 虚引用，只保留强引用）。

MAT 会自动提取多个选中对象各自到 GC Roots 的最短引用链，将重复的路径节点合并，最终生成一棵共享路径树。

功能 适用场景 核心价值
Path to GC Roots 单个可疑对象 定位单个对象的泄漏原因
Merge Shortest Paths to GC Roots 多个同类 / 批量可疑对象 定位所有对象的共同泄漏根节点

适用场景

Eclipse MAT专注于堆内存深度分析，其适用场景主要集中在内存相关问题的排查，核心场景如下：

  • 生产环境OOM问题排查：应用发生OOM（Out Of Memory）崩溃后，会生成堆快照文件，使用MAT分析该快照，可快速定位OOM的根源（如内存泄漏、大对象过多、堆内存配置不足）。
  • 内存泄漏深度排查：当应用内存持续增长、GC无法有效回收时，生成堆快照，通过MAT的支配树、引用链分析，精准定位泄漏的核心对象和问题代码，是内存泄漏排查的首选工具。
  • 大对象优化：定位堆内存中的大对象，分析其创建逻辑和引用关系，优化代码减少大对象创建，或采用分批次处理、内存映射等方式，降低内存占用。
  • 测试环境内存性能优化：在测试环境中，通过MAT分析堆快照，提前发现内存泄漏隐患和大对象问题，优化代码和内存配置，避免问题带入生产环境。

软件的内存泄漏业务场景

业务实现抽象

技术架构与界面分层

应用基于 JavaFX 构建桌面端图形界面，集成 Spring IoC 容器 实现业务对象的依赖注入与生命周期管理；整体界面采用主入口 + 多实例工作台的双层架构设计：

  1. 主界面（欢迎界面）：应用全局唯一的入口界面，与应用进程同生命周期，作为工作台的启动入口；
  2. 工作台模块：核心业务功能载体，支持用户同时打开 N 个独立实例，每个工作台拥有完全隔离的界面、上下文与业务数据。

核心对象模型与生命周期划分

  • 长生命周期对象（全局 / 应用级，常驻内存）

    • Spring 容器管理的单例 Bean（如全局主题管理器 ThemeManager、工具类、全局事件总线等）；
    • 应用主窗口（欢迎界面）、JavaFX 全局运行时对象。

  • 短生命周期对象（工作台级，随窗口创建 / 销毁）

    每个独立工作台对应一套专属对象，理论上随窗口关闭立即释放：

    • Workbench：工作台核心业务实体对象，单个工作台唯一标识；
    • WorkbenchContext：工作台上下文对象，封装 Workbench、页面配置、UI 组件引用、业务参数等核心上下文信息；
    • JavaFX Stage：工作台独立窗口容器，承载整个工作台的 UI 渲染；
    • 自定义 UI 组件：如 View 及其皮肤 ViewSkin（工作台内嵌功能组件）；
    • Spring 多实例（Prototype）页面对象：每个工作台专属的页面 Bean，非全局共享。

标准业务流程

  1. 应用启动：初始化 Spring 容器 → 加载全局单例 Bean → 展示欢迎主界面；
  2. 打开工作台：主界面触发操作 → Spring 创建多例页面对象 → 初始化 Workbench + WorkbenchContext → 创建 JavaFX 独立 Stage 窗口 → 加载嵌套层级 UI 组件 → 完成工作台展示；
  3. 关闭工作台：用户关闭 Stage 窗口 → 触发 JavaFX 界面销毁逻辑 → 断开所有对象引用 → 短生命周期对象被 JVM GC 回收。

问题描述

用户关闭任意一个工作台窗口（JavaFX Stage）后，该工作台对应的全套短生命周期对象无法被 JVM 垃圾回收，始终驻留内存：

  1. 核心业务对象：Workbench、WorkbenchContext 持续泄漏；
  2. UI 相关对象：工作台 Stage、内嵌自定义组件 ViewSkin 无法释放；
  3. Spring 对象：多实例页面对象残留，无法被容器销毁。

随着打开的工作台数量增加，应用内存占用持续上涨，长期运行会引发内存溢出、界面卡顿等问题。

预期结果

用户执行工作台关闭操作后：

  1. JavaFX 框架正常销毁工作台窗口及所有内嵌 UI 组件，自动触发组件销毁方法（如 dispose()）；
  2. 所有工作台专属短生命周期对象（Workbench/WorkbenchContext/Stage/UI 组件 / Spring 多例页面）无强引用残留；
  3. JVM 正常回收全部工作台相关对象，内存无泄漏，应用内存占用保持稳定。

内存分区

堆内存

JVM 用于存储对象实例、数组的核心区域，为内存监控重点。在 G1 垃圾收集器下，堆内存采用Region 分区模型，物理上划分为多个大小相等的独立区域（默认 1MB~32MB），逻辑上可分为以下内存池：

  • 内存池 G1 Eden Space：伊甸园区，新创建对象优先在此分配内存，是对象分配的主要区域。由多个 Eden Region 组成，占比通常约为年轻代的 80%

  • 内存池 G1 Survivor Space：幸存者区，存放 Eden 区 Young GC 后存活的对象。注意：G1 的 Survivor 区由多个 Survivor Region 组成，并非传统 GC 的固定 S0/S1 两区交替模式

  • 内存池 G1 Old Gen：老年代，存储长期存活、多次垃圾回收后仍未被回收的对象，由多个 Old Region 组成

    补充说明：G1 还有一个特殊的 Humongous Region（大对象区），用于存储大小超过 Region 容量 50% 的大对象。在部分监控工具中，大对象可能计入 Old Gen 或单独展示。

堆内存使用量（Heap Memory Usage）

核心定义：JVM 中用于存储对象实例的内存区域，是垃圾回收的主要区域，所有通过new创建的对象都分配在堆上。

关键参数 说明
Current heap size 当前堆内存使用量（已分配对象占用的内存）
Committed memory JVM 已向操作系统申请并获得的内存总量
Maximum heap size 堆内存的最大可用值（由-Xmx参数控制）
Init heap size JVM 启动时初始分配的堆内存（由-Xms参数控制）

工作原理：

  • 堆内存采用分代管理（新生代 + 老年代），G1 收集器将堆划分为多个大小相同的 Region（默认 1MB~32MB，必须为 2 的幂次方，最多 2048 个区域）
  • Region 大小由 -XX:G1HeapRegionSize 参数设置，默认值为堆大小/2048（自动计算为最接近的 2 的幂次方）
  • Young GC：回收 Eden 和 Survivor 区域，存活对象晋升到老年代或留在 Survivor 区
  • Mixed GC：G1 特有的混合回收，同时回收部分老年代 Region 和全部年轻代
  • Full GC：回收整个堆内存，G1 的 Full GC 采用单线程串行方式，应尽量避免

监控意义：

  • 持续增长且接近最大堆内存值可能导致 OOM: Java heap space
  • 频繁 GC 且回收效果不佳通常表示存在内存泄漏或需要调整堆大小
  • 若出现 Full GC，表明 G1 未能及时完成并发标记或堆空间严重不足，需重点排查

G1 收集器相关内存池

内存池 G1 Eden Space（G1 新生代 Eden 区）

核心作用：新生代的主要分配区域，绝大多数新创建的普通对象优先分配在 Eden 区。

关键特性：

  • G1 中整个堆被划分为多个固定大小的 Region（启动时确定，默认 1MB~32MB，为 2 的幂次方），Eden 区由若干个 Eden Region 组成。
  • Eden Region 的数量可动态调整，JVM 根据 GC 性能在指定范围内自动增减。
  • 巨型对象（Humongous Object）：大小超过 Region 50% 的对象直接分配到老年代的 Humongous Region，不经过 Eden 区。
  • 当 Eden 区分配空间不足时触发 Young GC，回收范围为整个年轻代（Eden + Survivor）：
    • 未达晋升年龄阈值的存活对象 → 复制到 Survivor 区
    • 达到晋升年龄阈值的存活对象 → 直接晋升到老年代
  • 新生代整体大小范围由 -XX:G1NewSizePercent（默认 5%）和 -XX:G1MaxNewSizePercent（默认 60%）控制，百分比基于整个堆总大小。

监控重点：

  • Eden 区快速填满且 Young GC 频繁：可能是短生命周期对象创建过多
  • Eden 区占用率持续偏低：可能是新生代设置过大，造成资源浪费
  • Young GC 后对象晋升率过高：会加速老年代增长，容易触发并发标记或 Mixed GC，需关注 -XX:MaxTenuringThreshold、对象存活时间等
  • Humongous 对象分配过多：可能导致老年代碎片化和 Full GC，需关注大对象分配场景
内存池 G1 Survivor Space（G1 新生代 Survivor 区）

核心作用：存储 Young GC 后存活的对象，作为 Eden 区与老年代之间的过渡区域，通过多次 GC 筛选对象以减少老年代压力。

关键特性：

  • G1 中 Survivor 区由多个动态分配的 Survivor Region组成，不存在传统 GC 固定的 From Space / To Space 双分区设计（与 Parallel、CMS 不同）。
  • 每次 Young GC 后，Eden 区与旧 Survivor 区中的存活对象被复制到另一组全新的 Survivor Region，对象年龄 +1。
  • 当对象年龄达到晋升阈值（默认 15，由 -XX:MaxTenuringThreshold 控制）时，晋升到老年代。
  • Survivor 区大小动态调整：G1 根据 GC 暂停时间、对象晋升情况自动调整 Survivor Region 数量；-XX:SurvivorRatio 在 G1 中基本不生效。
  • Survivor 空间不足处理：当 Survivor 区无法容纳所有存活对象时，多余对象直接晋升到老年代，该现象称为过早晋升；

监控重点：

  • Survivor 区频繁溢出：表示存活对象过多或 Survivor 区过小，可能导致老年代快速增长
  • Survivor 区利用率持续偏低：可能是新生代设置过大或对象存活率低
  • 对象平均晋升年龄过低：可能说明 Survivor 区容量不足，需关注 -XX:G1NewSizePercent 和 -XX:G1MaxNewSizePercent 配置
  • Young GC 后老年代增长率过高：可能是 Survivor 溢出导致对象过早晋升
内存池 G1 Old Gen（G1 老年代）

核心作用：存储长生命周期对象、从 Survivor 区达到年龄阈值晋升的对象，同时托管巨型对象（Humongous Object）；G1 主要通过 混合回收（Mixed GC） 对老年代做增量式回收，降低单次 GC 停顿。

关键特性：

  • 由多个固定大小的 Region 构成，包含普通老年代 Region（Old Region）\与*巨型对象 Region（Humongous Region）*，后者逻辑上归属于老年代管理。
  • 采用并发标记 + 增量回收模式，只回收部分收益最高的老年代 Region，避免整代回收带来的长 STW。
  • 当整个堆内存占用率达到阈值（默认 45%，由 -XX:InitiatingHeapOccupancyPercent 控制）时，启动并发标记周期。
  • 混合回收（Mixed GC）：并发标记完成后，在多次 GC 中依次回收「整个年轻代 + 收益高的部分老年代 Region」，不回收 Humongous Region。
  • 晋升失败（Promotion Failed）：对象需要晋升老年代但无连续空间，会直接触发退化 GC 甚至 Full GC。
  • G1 的 Full GC 默认为单线程串行回收，性能极差，是线上优化核心规避目标。

监控重点：

  • 老年代占用持续走高并逼近上限：多为长生命周期对象过多、对象晋升过快，可考虑调堆或优化对象生命周期。

  • 频繁发生 Full GC：常见诱因包括并发标记启动过晚、晋升失败、巨型对象过多导致碎片化、堆内存不足。

  • Humongous 对象过多：会造成老年代严重碎片化，且无法通过 Mixed GC 清理，极易触发 Full GC。

    并发标记周期触发过于频繁：一般是 IHOP 阈值设置过低，或对象晋升速率过快。

    Mixed GC 后老年代内存下降不明显：说明老年代对象存活率高、可回收空间少，往往伴随长期持有、缓存过大等问题。

非堆内存

用于存储类元数据、JIT 编译代码、类信息等数据，不参与堆内存的常规 GC 逻辑，包含以下内存池：

  • 内存池 Metaspace：元空间，JDK 8 及以上用于替代永久代，存储类元数据、方法信息等。位于本地内存，大小可动态调整，受系统内存限制（可通过 -XX:MaxMetaspaceSize 设置上限）
  • 内存池 Compressed Class Space：压缩类空间，配合指针压缩机制存储类元数据，是 Metaspace 的配套区域，用于减少 64 位系统下的内存开销
  • 三类 CodeHeap 内存池：用于存放 JIT 编译后的本地机器代码，分别为：
    • CodeHeap 'non-nmethods'：存储非方法代码（如虚拟机桩代码）
    • CodeHeap 'profiled nmethods'：存储经过性能分析的方法代码
    • CodeHeap 'non-profiled nmethods'：存储未经性能分析的方法代码

非堆内存使用量（Non-Heap Memory Usage）

核心定义：JVM 用于存储类元数据、编译后的代码、线程栈等非对象实例数据的内存区域。非堆内存与堆内存是 JVM 管理的两个独立区域，物理上独立管理，不受堆大小（-Xmx）限制，但受系统物理内存和 JVM 参数限制。

元数据相关内存池

内存池 Metaspace（元空间）

核心定义：Java 8+ 用于替代永久代（PermGen）的本地内存区域，主要存储类元数据（类结构、字段、方法、注解等）、方法字节码、运行时常量池（静态常量池部分）；字符串常量池（String Table） 已在 Java 7+ 移至Java 堆，不属于元空间。

关键特性：

  • 位于本地内存（Native Memory），不属于 JVM 堆；默认无上限，仅受操作系统物理内存与进程地址空间限制。

  • 内存管理采用Chunk 分配机制，按 Small/Medium/Large 三种块粒度，以类加载器为单位批量管理内存。

  • 类卸载默认开启：JVM 默认启用类卸载（-XX:+ClassUnloading），无需额外诊断参数；

    类可卸载需同时满足：该类所有实例已回收、类的 Class 对象无引用、类加载器已被 GC 回收。

  • 类加载器被回收时，其占用的元空间内存会整体批量释放，不单独管理单个类的元数据内存。

  • 压缩类空间（Compressed Class Space） 是元空间的专用子区域（并非独立于元空间），仅用于存储压缩指针模式下的类元数据。

  • 元空间不足时，会触发针对元空间的 GC（多为 Full GC），而非 Young GC。

核心参数：

参数 说明 默认值
-XX:MetaspaceSize 元空间GC 触发阈值（高水位线），并非初始大小；达到该值会尝试 GC 以释放元数据 约 21MB
-XX:MaxMetaspaceSize 元空间使用上限，超出会抛出 OutOfMemoryError: Metaspace 无限制
-XX:MinMetaspaceFreeRatio/-XX:MaxMetaspaceFreeRatio GC 后元空间空闲比例下限 / 上限，用于控制扩容与收缩 40%/70%
-XX:CompressedClassSpaceSize 压缩类空间上限，仅在开启类指针压缩时生效，属于元空间一部分 1GB

监控意义：

  • 元空间持续增长并逼近上限：大概率存在类加载器泄漏（如热部署未清理、自定义类加载器未释放、动态代理滥用）。
  • 频繁触发元空间相关 GC 但回收量低：说明类 / 类加载器无法卸载，而非空间设置过小。
  • 元空间使用波动剧烈：常见于大量动态类生成场景（CGLIB、ASM、Groovy、JSP 编译、反射代理等）。
  • 本地内存（Native Memory）持续上涨但堆稳定：优先排查元空间泄漏、CodeCache 或其他本地内存分配。
  • 类卸载量长期为 0：检查类加载器引用、线程上下文类加载器、静态缓存持有 Class 对象等问题。
内存池 Compressed Class Space（压缩类空间）

核心定义：64 位 JVM 启用 -XX:+UseCompressedClassPointers（默认开启）时，元空间内部一块独立的连续虚拟内存区域，专门用于存储 JVM 内部的 Klass 元数据结构，并基于压缩类指针进行寻址。

核心作用：

  • 配合压缩类指针，将对象头中指向类元数据的指针从 64 位压缩为 32 位，减少对象内存占用。
  • 必须使用连续虚拟地址空间，才能支持基于基地址的 32 位偏移寻址。
  • 与普通元空间分开管理：Klass 结构存在 Compressed Class Space，而方法字节码、常量池、注解等其他类元数据仍存放在普通 Metaspace 中。

关键特性：

  • 启用条件：
    • 64 位 JVM
    • -XX:+UseCompressedOops 开启（默认开启）
    • -XX:+UseCompressedClassPointers 开启（默认开启）
    • 堆大小一般不超过 32GB，否则压缩指针机制会自动失效
  • 空间大小限制
    • 压缩类空间的理论寻址上限为 4GB（32 位偏移）
    • -XX:CompressedClassSpaceSize 实际建议最大设置为 3GB（需预留部分地址空间）
  • 内存归属
    • 属于元空间的子区域，但使用独立连续虚拟内存；
    • -XX:MaxMetaspaceSize 不限制 Compressed Class Space，二者空间上限相互独立。
  • 存储内容
    • 仅存储 JVM 内部的 Klass 结构体（类的元数据描述）
    • 不存储方法代码、运行时常量池、注解等其他类元数据。

核心参数：

参数 说明 默认值
-XX:+UseCompressedClassPointers 启用压缩类指针与压缩类空间 默认开启
-XX:CompressedClassSpaceSize 压缩类空间最大容量 1GB
-XX:+UseCompressedOops 启用压缩普通对象指针，是压缩类空间的前置条件 默认开启（堆 < 32GB）

监控意义：

  • 压缩类空间溢出会抛出：java.lang.OutOfMemoryError: Compressed class space
  • 溢出常见原因：加载类数量极多（大量动态代理、OSGi、热部署、类加载器泄漏）
  • 解决方案：
    • 适当调大 -XX:CompressedClassSpaceSize（建议最大 3GB）
    • 优化动态类生成、检查类加载器泄漏
    • 避免无限制创建动态代理类
  • jstat 监控：通过 jstat -gc <pid> 查看 CCSC（总容量）、CCSU（已使用大小）

注意事项：

  • 堆内存超过约 32GB 时，JVM 会自动关闭压缩指针，压缩类空间不再使用。
  • 压缩类空间使用连续虚拟内存，不要求物理内存连续。
  • 该区域仅在 64 位 JVM 存在，32 位 JVM 无此区域。

代码缓存相关内存池（CodeHeap）

Java 9 + 将 CodeCache（代码缓存）分为三个独立的内存池，优化不同类型代码的存储和管理。

内存池 CodeHeap profiled methods（Profiled 代码堆）

核心定义：Java 9+ 代码缓存三段式分区架构中的中间区域，用于存储带有性能采集信息的 JIT 编译后机器码（profiled nmethods），对应分层编译的 Tier 2、Tier 3 层级。

核心作用

  • 存储带性能采集数据的中等优化等级方法代码，为后续深度优化提供依据
  • 采集方法调用次数、分支跳转、类型信息等 profiling 数据，用于判断是否需要升级为 C2 最高优化等级
  • 作为分层编译的中间过渡层，符合热度条件的方法会被重新编译并晋升至 non-profiled nmethods 区域

关键特性：

  • 优化程度：中等优化，保留完整性能采集信息，不做激进优化。
  • 生命周期
    • 高热度方法：会被 C2 重新编译，升级到 non-profiled 区域，原有 profiled 版本可被清理
    • 低热度 / 失效方法：方法去优化、类卸载后，代码缓存可被清扫回收
  • 空间大小：大小由 -XX:ProfiledCodeHeapSize 指定，是三段式代码缓存的一部分，总上限受 -XX:ReservedCodeCacheSize 约束。
  • 清理机制：通过 CodeCache 专属清扫（Sweep）机制回收无效编译代码，不属于 Java 堆 GC。

核心参数：

参数 说明 默认值（64 位 Server JVM）
-XX:ProfiledCodeHeapSize Profiled nmethods 代码堆最大容量 ~122MB（Java 9+）
-XX:+TieredCompilation 启用分层编译（该分区存在的前提） 默认开启
-XX:InitialCodeCacheSize 代码缓存初始大小 ~2.5MB
-XX:ReservedCodeCacheSize 整个代码缓存（三段合计）预留总大小 240MB
-XX:NonNMethodCodeHeapSize non-nmethods 代码堆大小 ~5.8MB
-XX:NonProfiledCodeHeapSize non-profiled nmethods 代码堆大小 ~122MB

监控意义：

  • 区域满的后果：
    • JVM 停止对新方法进行 profiled 编译
    • 热点方法无法进入 Tier3 采集数据，更无法晋升到 C2 最高优化
    • 大量方法只能以解释执行或低优化等级运行，应用吞吐量显著下降
  • 快速填满的可能原因：
    • 方法数量庞大、中等热度方法过
    • 反射 / 动态代理频繁生成新方法、Lambda 大量创建
    • 分层编译阈值偏低，大量方法快速进入 Tier3
  • 监控指标：
    • 使用率长期偏高 → 适当调大 -XX:ProfiledCodeHeapSize
    • 清扫频繁但空间下降不明显 → 多为长期驻留的编译方法，无明显泄漏
    • 配合 jcmd <pid> Compiler.codecache、jcmd <pid> VM.code_cache 查看分区使用
内存池 CodeHeap non-nmethods（Non-method 代码堆）

核心定义：Java 9+ 代码缓存三段式分区架构中的基础设施区域，用于存储非方法类型的编译代码（non-nmethods），包括 JVM 内部使用的 Stub、Adapter、JNI 方法等辅助代码。

核心作用：

  • 存储JVM 运行时基础设施代码，支撑 JIT 编译器和解释器的正常运作
  • 存放字节码解释器存根、方法调用适配器、异常处理存根等系统级代码
  • 提供JNI _native 方法绑定代码，支持 Java 与本地代码的交互

关键特性：

  • 存储内容（非 nmethod 类型代码）：

    | 代码类型 | 说明 |
    | —————— | ———————————————————————— |
    | Stub | 字节码解释器存根、异常处理存根、安全点存根 |
    | Adapter | 方法调用适配器（C1/C2 编译器与解释器之间的桥接） |
    | JNI Code | JNI 方法绑定的本地代码桩 |
    | Runtime Stub | 运行时辅助代码（如 GC 屏障、锁操作等） |

  • 优化程度：不适用（非方法代码，无优化层级概念）

  • 生命周期：常驻内存，JVM 运行期间基本稳定，很少被回收

  • 空间大小：由 -XX:NonNMethodCodeHeapSize 指定，默认约 5.8MB

  • 独立性：与其他两个 CodeHeap 独立管理，互不影响

  • 内存归属：属于非堆内存（Non-Heap），不受 -Xmx 限制

核心参数：

参数 说明 默认值（64 位 Server JVM）
-XX:NonNMethodCodeHeapSize non-nmethods 代码堆最大容量 ~5.8MB
-XX:InitialCodeCacheSize 代码缓存初始大小 ~2.5MB
-XX:ReservedCodeCacheSize 整个代码缓存（三段合计）预留总大小 240MB
-XX:ProfiledCodeHeapSize profiled nmethods 代码堆大小 ~122MB
-XX:NonProfiledCodeHeapSize non-profiled nmethods 代码堆大小 ~122MB

监控意义：

  • 区域满的后果
    • JVM 无法生成新的 Stub/Adapter 代码
    • JIT 编译器可能完全失效，所有代码回退到解释执行
    • 应用性能严重下降，甚至无法正常运行
  • 溢出概率
    • 该区域内容在 JVM 启动后基本稳定
    • 正常情况下不会持续增长
    • 若出现异常增长，通常表示JVM 内部错误或 Bug
  • 监控指标
    • 使用率应保持稳定（启动后基本不变）
    • 若持续增长 → 可能存在 JVM Bug 或异常类加载行为
    • 配合 jcmd <pid> VM.code_cache 查看各 CodeHeap 使用情况
  • 解决方案
    • 正常情况下无需调整该区域大小
    • 若确实溢出，可尝试增加 -XX:NonNMethodCodeHeapSize
    • 更应关注是否存在 JVM 版本 Bug，考虑升级 JVM
    • 检查是否有异常的动态类生成或类加载器泄漏
内存池 CodeHeap non-profiled nmethods（Non-profiled 代码堆）

核心定义：Java 9+ 代码缓存三段式分区架构中的最终优化层，用于存储不带性能分析信息的编译方法代码（non-profiled nmethods）。

核心作用：

  • 存储最高优化等级（Tier 4）的热点方法代码，提供最佳运行时性能
  • 存储最低优化等级（Tier 1）的快速编译代码，用于快速启动和冷方法执行
  • 作为分层编译的最终存储区，方法进入该区域后不再收集性能数据，完全专注于执行效率。

关键特性：

  • 优化策略：
    • 激进优化：由于不保留 profiling 数据，C2 编译器可进行最大程度的优化（如大胆内联、锁消除）
    • 代码体积：优化后的代码体积通常较大，但执行速度最快
  • 生命周期：
    • 长生命周期：存储的是经过验证的热点方法或基础冷方法，通常在 JVM 运行期间长期驻留
    • 回收机制：仅在类卸载或长时间未使用时，通过 CodeCache Sweep 机制回收
  • 空间大小：由 -XX:NonProfiledCodeHeapSize 指定，默认约 122MB
  • 独立性：与 profiled nmethods 独立，避免高优化代码挤占中间层空间

核心参数：

参数 说明 默认值（64 位 Server JVM）
-XX:NonProfiledCodeHeapSize non-profiled nmethods 代码堆最大容量 ~122MB
-XX:+TieredCompilation 启用分层编译（前提条件） 默认开启
-XX:ReservedCodeCacheSize 整个代码缓存（三段合计）预留总大小 240MB
-XX:ProfiledCodeHeapSize profiled nmethods 代码堆大小 ~122MB
-XX:NonNMethodCodeHeapSize non-nmethods 代码堆大小 ~5.8MB

监控意义：

  • 区域满的后果
    • JVM 停止将方法编译为 Tier 4（最高优化） 或 Tier 1
    • 即使方法非常热点，也只能停留在 Tier 3（中等优化），无法发挥极致性能
    • 应用吞吐量达到瓶颈，CPU 利用率可能异常偏高（因优化不足导致指令数增加）
  • 持续增长的含义
    • 正常现象：表示应用中有大量稳定的热点方法被成功优化并驻留
    • 潜在风险：若持续填满且伴随性能下降，说明代码缓存总量不足以支撑应用的热点方法数量
  • 监控指标
    • 使用率接近 100%：必须调整 -XX:NonProfiledCodeHeapSize 或 -XX:ReservedCodeCacheSize
    • 对比 profiled nmethods 使用率：若 non-profiled 占比过高，说明应用已进入稳定运行期，大量方法已完成优化
  • 解决方案
    • 增加 -XX:NonProfiledCodeHeapSize（注意总和不能超过 -XX:ReservedCodeCacheSize）
    • 增加 -XX:ReservedCodeCacheSize 以容纳更多优化代码（如设为 512MB 或更高）
    • 检查是否有过多的动态生成类导致方法数量爆炸

补充说明

关于过早晋升、晋升失败和疏散失败

过早晋升（Premature Promotion）
定义

年轻代的对象还未达到合理的晋升年龄（本应留在 Survivor 继续筛选），就被迫提前晋升到老年代的现象。

简单来说：本该 “年轻” 的对象，提前进入了 “老年区”。

核心原因

最主要的触发因素是Survivor Region 空间不足：

  • YGC 时，Eden 区存活的对象需要转移到 Survivor 区，但 Survivor 区剩余空间不足以容纳这些对象；
  • G1 为了完成 YGC，会直接将这些 “没到年龄” 的对象强制晋升到老年代，而非留在 Survivor。

其他次要原因：

  • Survivor 区配置过小（如-XX:SurvivorRatio设置不合理）；
  • 应用短生命周期对象异常增多，或对象存活时间超出预期；
  • YGC 频率过高，Survivor 区来不及 “筛选” 对象就被占满。
影响
  • 老年代被大量短命对象占据，老年代空间快速耗尽；
  • 触发更频繁的 Mixed GC（混合回收），甚至直接触发单线程、性能极差的 Full GC，导致应用 STW（Stop-The-World）时间大幅增加；
  • 堆内存利用率降低，垃圾回收效率下降。
解决方案
  • 调大 Survivor 区 / 年轻代整体比例：通过-XX:G1NewSizePercent（年轻代最小占比）、-XX:G1MaxNewSizePercent（年轻代最大占比）提升年轻代空间，间接增加 Survivor 可用空间；
  • 调整晋升年龄阈值：通过-XX:MaxTenuringThreshold增大对象晋升到老年代的年龄（默认 15），让对象在 Survivor 多停留几次 YGC；
  • 优化应用代码：减少短生命周期对象的创建，或缩短其存活时间；
  • 增大堆内存：从整体上提升 Survivor 和老年代的可用空间。
晋升失败（Promotion Failure）
定义

GC 过程中，存活对象需要从年轻代（Eden/Survivor）晋升到 Survivor 或老年代时，目标 Region 没有足够的空闲空间，导致晋升操作无法完成的现象。

⚠️ 晋升失败≠OOM（内存溢出），前者是 “暂时空间不足”，后者是 “彻底无空间可用”。

核心原因
  • 老年代空闲 Region 不足：YGC 时要晋升的对象量过大，老年代没有足够的空 Region 容纳；
  • 大对象（Humongous Object）占用过多老年代空间：G1 中大于 Region 一半的对象为大对象，直接分配在 Humongous Region（归属老年代），若大对象过多会挤占老年代可用空间；
  • 并发标记（CM）未及时完成：G1 的并发标记还没清理掉老年代的垃圾，导致老年代空间无法释放；
  • 堆内存整体不足：堆总容量无法满足对象晋升的需求。
影响

晋升失败会直接触发 G1 的疏散失败（Evacuation Failure）：

  • G1 会立即停止当前的 YGC，转而触发 Full GC（单线程标记 - 清除 - 整理）；
  • Full GC 的 STW 时间通常是 YGC 的几十倍甚至上百倍，会导致应用卡顿、响应超时；
  • 若 Full GC 后仍无足够空间，会进一步触发OutOfMemoryError。
解决方案
  • 增大堆内存：优先提升老年代的可用空间（避免仅调大年轻代）；
  • 优化大对象使用：减少大对象的创建，或通过-XX:G1HeapRegionSize调整 Region 大小（让大对象适配 Region，减少 Humongous Region 占用）；
  • 调整混合回收触发时机：降低-XX:G1HeapWastePercent（默认 5%），让 G1 更早触发 Mixed GC 清理老年代垃圾；
  • 监控并修复内存泄漏：内存泄漏会持续占用老年代空间，是晋升失败的隐性诱因；
  • 调整 YGC 触发阈值：通过-XX:G1YoungGenSizeIncrementPercent等参数，避免 YGC 过于频繁导致晋升压力集中。
疏散失败（Evacuation Failure）

疏散失败是 G1 在 Region 复制 / 疏散阶段因目标空间不足或对象被钉住（Pinned） 导致的失败，会触发 STW 的 Full GC，显著增加暂停时间并损害应用性能。最常见的诱因是to-space 耗尽（To-space Exhausted），本质是晋升目标空间不足。

定义与本质

疏散失败（Evacuation Failure）是 G1 在执行复制 - 清除（Evacuation）阶段时，无法为待疏散的存活对象找到足够空闲 Region 进行安置，导致复制操作无法完成的现象。

  • 核心场景：主要发生在 Young GC（YGC）或 Mixed GC 过程中，当 G1 尝试将 Eden/Survivor/ 老年代 Region 中的存活对象复制到新 Region 时
  • 本质区别：与传统晋升失败（Promotion Failure）不同，G1 的疏散失败是更广义的概念，涵盖所有 Region 复制失败场景，而晋升失败特指年轻代对象晋升到老年代时的空间不足问题
触发条件与常见原因

  • 主要触发条件（两类）

    | 触发类型 | 具体描述 | 日志标识 |
    | ————————————- | —————————————————————————- | —————————————————— |
    | Allocation Failure | 找不到足够空闲 Region 容纳待复制的存活对象 | Evacuation Failure: AllocationOracle |
    | Pinned Object Failure | 存在被 JNI 或本地代码钉住（Pinned）的对象，无法移动 | Evacuation Failure: PinnedOracle |

  • 最常见诱因：To-space 耗尽（To-space Exhausted）

    这是 G1 中最典型的疏散失败场景，表现为 “目标空间（Survivor / 老年代）无可用 Region”Oracle：

    • Young GC 时，Eden 区存活对象需转移到 Survivor 区，但 Survivor 区无足够空间
    • 老年代空间碎片化严重，无法提供连续 Region 容纳晋升对象
    • 并发标记（CM）未及时完成，老年代垃圾未被清理，导致可用空间不足
    • 大对象（Humongous Object）占用过多老年代空间，挤占晋升空间

  • 其他常见原因

    • 堆内存整体不足（-Xmx 设置过小），无法满足对象复制需求
    • G1ReservePercent（默认 10%）设置过低，保留的晋升空间不足
    • 应用短时间内创建大量存活对象，超出 G1 的疏散能力
    • JNI 代码或本地方法调用导致对象被钉住，无法移动Oracle
发生机制与处理流程

当疏散失败发生时，G1 会执行以下应急处理：

  1. 保留已复制对象：已成功移动到新位置的存活对象保持不动
  2. 放弃剩余复制：不再尝试复制未移动的对象
  3. 调整引用关系：仅修正对象间的引用，确保对象图完整性
  4. 触发 Full GC：若疏散失败无法通过上述调整解决，G1 会立即触发 STW 的Full GC（单线程标记 - 清除 - 整理算法），对整个堆进行回收
对应用的影响
  1. STW 时间剧增：Full GC 的暂停时间通常是 Young GC 的几十倍甚至上百倍，直接导致应用响应超时、卡顿
  2. 内存碎片化加剧：疏散失败后未复制的对象留在原地，加剧堆内存碎片化
  3. GC 效率下降：频繁的疏散失败会导致 G1 退化为 Full GC 主导，失去其低延迟优势
  4. 解决方案与调优策略OOM 风险：若 Full GC 后仍无足够空间，会触发OutOfMemoryError

    | ———————————— | —————————————— | —————————————————————————————— |
    | -Xmx/-Xms | 增大堆内存，尤其是老年代空间 | 确保堆内存能容纳应用峰值对象数量 |
    | -XX:G1ReservePercent | 保留给晋升操作的空闲空间比例 | 从默认 10% 提升至 20%~25%，预留更多晋升空间 |
    | -XX:G1HeapRegionSize | Region 大小（1MB~32MB，2^N） | 若有大量大对象，调整为适配大对象的大小，减少 Humongous Region 占用 |

  2. 年轻代与晋升策略优化

    • 调整年轻代比例：通过-XX:G1NewSizePercent（最小）和-XX:G1MaxNewSizePercent（最大）平衡年轻代与老年代空间
    • 增大 Survivor 区：通过-XX:SurvivorRatio降低 Eden/Survivor 比例，减少过早晋升
    • 调整晋升年龄阈值：-XX:MaxTenuringThreshold（默认 15），让对象在 Survivor 多停留几次 YGCOracle

  3. 并发标记与混合回收调优

    • 降低-XX:G1HeapWastePercent（默认 5%），让 G1 更早触发 Mixed GC 清理老年代垃圾Oracle
    • 调整-XX:G1MixedGCCountTarget（默认 8），控制混合回收次数，避免老年代垃圾堆积
    • 增大-XX:G1MixedGCLiveThresholdPercent（默认 85%），只回收存活对象少的老年代 Region

  4. 大对象与钉住对象处理

    • 减少大对象创建：拆分大对象或使用池化技术复用对象
    • 优化 JNI 代码：避免长时间钉住对象，尽量缩短本地方法调用时间
    • 监控钉住对象：通过-Xlog:gc+heap=debug日志分析钉住对象情况

Java中的锁与监视器

Java 中的锁（Lock） 是实现多线程同步的上层抽象，监视器（Monitor，管程） 是 JVM 底层实现锁机制的核心原语。

Java 锁机制

锁的核心作用：强制多线程串行访问共享资源，保证并发操作的原子性、可见性、有序性，杜绝数据错乱、线程安全问题。

锁的分类

内置锁（Synchronized 隐式锁）

层级：JVM 原生实现，字节码级别（monitorenter/monitorexit）

使用方式：修饰实例方法、静态方法、同步代码块

管理方式：JVM 自动加锁 / 释放锁，不会产生锁泄漏

核心特性：可重入独占锁（同一线程可重复获取同一把锁）、默认非公平锁

底层依赖：完全基于监视器（Monitor）实现，是 Java 最基础、最通用的锁

显式锁（JUC Lock 显式锁）

层级：JDK 代码级别（java.util.concurrent.locks）

核心实现：ReentrantLock（可重入锁）、ReentrantReadWriteLock（读写锁）

管理方式：手动调用 lock() 加锁、unlock() 释放锁（必须配合 finally）

优势：支持超时获取锁、可中断、公平锁、多条件等待，灵活性远超内置锁

JVM 锁升级机制

为降低锁开销，JVM 会根据线程竞争程度自动升级锁，逐级提升性能：

偏向锁：无竞争时，锁偏向第一个线程，无任何同步开销

轻量级锁：少量竞争，线程通过自旋（CAS） 尝试获取锁，不阻塞

重量级锁：激烈竞争，自旋失败，升级为监视器锁，线程阻塞

监视器（Monitor）

定义

监视器（Monitor）= JVM 内置同步管程，是 Synchronized 内置锁的唯一底层实现。

关键规则：每个 Java 对象在堆内存中，都绑定一个唯一的 Monitor 对象

监视器的三大核心结构

监视器通过三个组件管理所有竞争锁的线程，是线程阻塞、等待的直接载体：

组件 英文 作用 线程状态
锁持有者 Owner 唯一持有锁的线程，正在执行同步代码 Running（运行）
锁竞争队列 Entry Set 所有尝试获取锁但失败的线程排队区 Blocked（锁阻塞）
等待队列 Wait Set 已获取锁、但调用 wait() 主动释放锁的线程排队区 Waiting（等待）

监视器完整工作流程（串行化执行）

  1. 线程竞争锁

    多线程同时进入同步代码，未获取锁的线程直接进入 Entry Set，状态变为 锁阻塞（Monitor）。

  2. 获取锁

    锁释放后，Entry Set 中一个线程被唤醒，成为 Owner，开始执行同步代码。

  3. 主动等待

    Owner 线程调用 wait()/wait(timeout) → 立即释放锁 → 进入 Wait Set → 状态变为等待。

  4. 唤醒等待

    其他线程调用 notify()/notifyAll() → Wait Set 线程被唤醒 → 重新进入 Entry Set 竞争锁。

  5. 释放锁

    Owner 执行完同步代码 → JVM 自动释放锁 → Entry Set 线程继续竞争。

监视器核心特性

  • 独占性：同一时间仅 1 个线程 能持有锁，保证同步代码串行执行
  • 可重入性：持有锁的线程可重复进入同一监视器的同步代码，避免自死锁
  • 自动调度：JVM 全权管理线程入队、唤醒、锁释放，无需开发干预
  • 性能开销：重量级监视器锁会触发线程阻塞 / 唤醒，是并发性能瓶颈的主要来源

Java内存泄漏

关于Java内存泄漏

Java 拥有自动垃圾回收（GC）机制，但内存泄漏并非内存物理丢失，而是长生命周期的对象意外持有短生命周期对象的强引用，导致短生命周期对象完成业务后，无法被 GC 判定为垃圾回收，最终堆内存持续被占用，引发频繁 Full GC、程序卡顿，最终抛出 OutOfMemoryError（OOM）。
