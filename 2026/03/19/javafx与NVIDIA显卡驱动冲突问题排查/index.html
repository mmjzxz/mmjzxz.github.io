javafx与NVIDIA显卡驱动冲突问题排查

1.问题/现象

javafx通过Maven+Launch4j打包成exe后, 在NVIDIA显卡驱动更新至576.80版本后的某个版本后，软件无法启动。

2.问题定位

2.1 事件查看器

通过Windows事件查看器查看软件运行崩溃日志(事件查看器-Windows日志-应用程序)。

日志信息如下：

错误应用程序名称: javaw.exe，版本: 17.0.2.0，时间戳: 0x4031b0a7
错误模块名称: nvldumdx.dll，版本: 32.0.15.8088，时间戳: 0x6885c3af
异常代码: 0xc0000409
错误偏移量: 0x0000000000074d24
错误进程 ID: 0x420c
错误应用程序启动时间: 0x01dc4725da101272
错误应用程序路径: D:\软件\jre\bin\javaw.exe
错误模块路径: C:\Windows\System32\DriverStore\FileRepository\nv_dispi.inf_amd64_fe5f369669db2f36\nvldumdx.dll
报告 ID: 0d00f5b6-2dc1-4743-9388-cad4eb69694a
错误程序包全名:
错误程序包相对应用程序 ID:

根据日志信息可以定位到javaw.exe运行时，调用了nvldumdx.dll中某个方法，导致程序崩溃。

注：并不是所有Windows事件查看器都能看到软件运行崩溃日志。

2.2 ProcDump

下载ProcDump压缩包，解压后得到procdump.exe，64位系统使用procdump64.exe。

将procdump64.exe放到javaw.exe同目录下。

以管理员身份打开cmd，切换到javaw.exe所在目录，执行以下命令：procdump64.exe -ma -e -t -w javaw.exe

参数 说明
-ma 捕获完整内存转储
-e 监听程序异常，触发崩溃时立即抓dump
-t 程序终止时也生成dump
-w 等待javaw.exe进程启动，启动后自动开始监听

保持cmd窗口打开，正常启动软件，复现问题。

程序崩溃后，cmd窗口自动生成dump(.dmp)文件，保存在当前目录下。

  • Unhandled exception: C0000409

    对应在事件查看器里看到的错误代码

  • Security check failure or stack buffer overrun - code c0000409

    系统在此应用程序中检测到基于堆栈的缓冲区溢出。此超限可能会允许恶意用户控制此应用程序

  • Subcode: 0x5 FAST_FAIL_INVALID_ARG

    当程序在 Windows 上触发 subcode: 0x5 FAST_FAIL_INVALID_ARG 时，意味着向某个函数传递了无效参数，并且 C 运行时(CRT)或安全检查机制调用了 快速失败(Fast Fail) 来立即终止进程

  • nvldumdx!useCFGModules+0x3f594

    nvldumdx：崩溃发生在 NVIDIA 驱动模块里

    useCFGModules+0x3f594：驱动里具体的函数名和偏移地址

    CFG = Control Flow Guard(控制流防护，微软的一种安全机制)

  • int 29h

    INT 29H 是一个用于快速失败的中断指令，通常用于在程序检测到严重错误时立即终止执行，在 Windows 8 及更高版本中被设计为 __fastfail

STACK_TEXT是崩溃时的函数调用栈，从下往上看是「调用顺序」，从上往下看是「崩溃发生点」，核心链路如下：

  1. JavaFX 渲染引擎发起调用

    prism_d3d!Java_com_sun_prism_d3d_D3DPipeline_nInit+0x75JavaFX 的 Prism D3D 渲染引擎(prism_d3d.dll)通过 JNI 调用D3DPipeline_nInit函数，尝试初始化 Direct3D 硬件渲染

  2. 调用 Windows Direct3D 系统库

    d3d9!Direct3DCreate9Ex+0x18
    d3d9!Direct3DCreate9Impl+0xb0
    d3d9!InternalDirectDrawCreate+0x235
    Prism 引擎调用 Windows 系统的d3d9.dll(Direct3D 9 核心库)，请求创建 Direct3D 渲染上下文

  3. 系统库加载 NVIDIA 驱动核心模块

    ntdll!LdrLoadDll+0xe4
    ntdll!LdrpLoadDllInternal+0x19a
    nvldumdx!OpenAdapter12+0x76e2
    Windows 的ntdll.dll(系统核心库)响应 Direct3D 的请求，加载 NVIDIA 驱动的nvldumdx.dll，并调用其OpenAdapter12函数(打开显卡适配器，建立 GPU 通信)

  4. 驱动 CFG 校验触发崩溃

    nvldumdx!useCFGModules+0x3f594

    ExceptionAddress: 00007ff99c695074 (nvldumdx!useCFGModules+0x000000000003f594)

    nvldumdx.dll执行useCFGModules函数(驱动的 CFG 控制流防护校验)，在检查 Java 进程传递的参数时，判定为「非法参数」，直接触发int 29h(Windows 中断指令)，终止javaw.exe进程

2.4 渲染管线优先级

在不配置额外启动参数的情况下，JavaFX 会根据运行的操作系统，预设不同的默认渲染管线优先级，主流系统默认顺序如下：

操作系统 默认优先级顺序 说明
Windows d3d,es2,sw 优先尝试 Direct3D(Windows 专属硬件加速)，失败则尝试 OpenGL ES 2.0，最后回退到软件渲染 (sw)
macOS es2,sw 优先尝试 OpenGL ES 2.0(macOS 无 Direct3D)，失败则回退到软件渲染
Linux es2,sw 优先尝试 OpenGL ES 2.0，失败则回退到软件渲染

在Windows系统下，JavaFX默认优先通过d3d渲染，从WinDbg异常分析报告可知在调用过程中也是调用d3d相关dll。

注：关于为什么.l4j.ini文件中配置了相关参数依然不生效的问题，Launch4j打包后的exe文件和.l4j.ini文件必须在同目录、同名的情况下才会生效。

2.5 排查d3d调用异常问题

但是，对于javafx软件来说，官方并未提供es2相关的dll，因此在设置-Dprism.order=es2,sw并且开启-Dprism.verbose=true的情况下，可以看到程序启动时也并未使用es2，而是直接失败并回退到sw渲染。由于追求渲染效率，回退到sw渲染并不在考虑范围内，因此需要继续排查d3d调用显卡驱动异常的具体原因。

2.5.1 排查思路

在更换不同的dll、通过其他javafx软件验证后，基本可以定位到问题还在于程序本身。排查方向如下：

  • 打包方式
  • 工程中的部分代码
  • 工程中的依赖

按照上述几种方式，简单方法就是将工程中的每个模块依次删除以及将有疑点的代码删除后验证打包后的软件是否可以运行，最终定位到start模块和framework.main模块(start模块中引用了framework.main模块)。

2.5.2 具体原因

在工程只剩下start模块和framework.main模块并且将start模块中的framework.main依赖删除后，软件可以运行。

由于framework.main模块中不包含任何代码和依赖，最终只能怀疑framework.main的模块名称。

导致d3d调用nvidia显卡驱动失败的原因便是代码中的某个模块名称携带.main，只需要将这个模块名称改成其他名称，软件即可运行。

(具体原理不清楚……)

附 Prism渲染管线说明

渲染管线 含义 作用
d3d Direct3D，微软专属的 3D 图形 API，Windows 系统下的硬件加速渲染管线，是 JavaFX 在 Windows 上的首选渲染方式 直接调用 Windows 系统的 Direct3D 接口，将 UI 渲染任务交给显卡(GPU)处理，性能最高、效率最好；仅支持 Windows 系统，macOS/Linux 无此选项；依赖显卡驱动对 Direct3D 的支持，若驱动老旧 / 缺失，会自动回退到下一个渲染模式
es2 OpenGL for Embedded Systems 2.0(嵌入式系统专用 OpenGL 子集)，跨平台的硬件加速渲染管线，是 macOS/Linux 的首选，也是 Windows 下 d3d 失败后的备选 基于 OpenGL 标准，可在 Windows/macOS/Linux 全平台使用，调用显卡的 OpenGL 接口完成硬件加速；相比 d3d，兼容性更广(尤其是跨平台场景)，但在 Windows 上性能略低于原生 d3d；要求显卡支持 OpenGL ES 2.0 或更高版本(主流显卡均支持)
sw Software Rendering(软件渲染)，纯 CPU 渲染管线，无硬件加速，是所有场景下的最终兜底方案 完全依靠 CPU 计算完成 UI 渲染，不调用任何显卡资源；兼容性 100%(只要有 CPU 就能运行)，但性能最差，复杂 UI / 动画会明显卡顿；仅在显卡不支持硬件加速(如老旧显卡、无 GPU 的虚拟机、驱动异常)时启用。
